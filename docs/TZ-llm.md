# ТЗ: AI-анализ срока эпика

Плагин Jira OhMyGant, версия на момент ТЗ — 1.33.0.

## 1. Цель

Менеджеру нужен ответ «когда эпик будет **готов**» — принят заказчиком и работает на проде, — с
вероятностью, а не дата конца разработки. Сейчас прогноз плагина считает только разработку, каждый
эпик отдельно и не знает про бизнес-тест.

Нужно: по кнопке напротив эпика запустить **AI-анализ**, который

1. строит вероятностный срок готовности — **95-й перцентиль**;
2. учитывает **долю потока** команд, которая достаётся эпику по работе людей;
3. учитывает **влияние эпиков друг на друга**: освобождение команд, когда другие эпики заканчиваются,
   и блокировки из-за загрузки людей в спринтах;
4. закладывает **бизнес-тест** — срок, типичный для этого заказчика, с поправками LLM и с учётом
   задач-заглушек, которые менеджер ставит на время отладки;
5. показывает бизнес-тест на Ганте **жёлтой штриховкой**;
6. по наведению на срок **объясняет**, почему он такой.

## 2. Принятые решения

| Вопрос | Решение |
|---|---|
| Что такое «готово» | Статус категории «Готово»: заказчик принял, функционал на проде. Срок исполнения эпика сравнивается с этой датой |
| Бизнес-заказчик | Автор (постановщик) эпика — поле из существующей настройки «Постановщик эпика» (по умолчанию Reporter) |
| Статус бизнес-теста | «БИЗНЕС ТЕСТ». Настройка «Статусы бизнес-теста» со значением по умолчанию `БИЗНЕС ТЕСТ`; сравнение без учёта регистра |
| Задачи-заглушки | Задачи, которые менеджер создаёт на время отладки и бизнес-теста («Задача заглушка», «Отладка»), обычно в конце спринта. Это **время бизнес-теста, а не разработка**: в остаток разработки и в историю потока не идут. Находит код по признакам из настройки, LLM — остальные (А4) |
| Блокировки | **Вычисляет LLM по загрузке людей в спринтах**: кто из людей эпика перегружен задачами других эпиков и в каких спринтах. Загрузка — по задачам в спринтах (существующий расчёт «По людям»), ёмкость — из настроек спринта. Связи Jira для блокировок не используются |
| Кто считает срок | **Код плагина**: Монте-Карло по потоку команд (А2). LLM даёт поправки в жёстких границах: коэффициент к сроку приёмки, блокировки, заглушки, отсутствие заказчика (А4). Числа в объяснении — только из расчёта |
| Что переиспользуем | Поток команд и долю эпика (`flow.js`: `buildFlow`, `epicShare`, `forecastShare`), команды людей (`flowTeamOf`: «Команда» → Tempo → доска), загрузку людей по спринтам (`agg.personLoad`) и ёмкость спринта (`sprintCapacity`: «Длительность спринта» × «Часов в рабочем дне»), фоновый поток вычислений (`forecast.worker.js`), привязку даты к шкале (`gantt.dueInfo`), постановщика эпика (`mapEpic`) |
| LLM | ChatGPT (OpenAI) или DeepSeek по ключу API. Оба отвечают в формате OpenAI Chat Completions — один клиент на `fetch`, без SDK |
| Передача данных | Согласована. Отправляются описание, комментарии, задачи и истории анализируемого эпика, загрузка его людей, список выбранных эпиков, статистика заказчика. Любые проекты |
| Календарь | Производственный календарь РФ из репозитория [d10xa/holidays-calendar](https://github.com/d10xa/holidays-calendar): файл `json/calendar.json`, плюс ручные правки (А8) |
| Где хранится результат | В общей базе `jiragantt`, хранилище `aiForecasts` (схема — `src/js/db.js`). Календарь и статистика приёмок — в `meta` |
| Запуск | Только по кнопке. Автоматического пересчёта нет: после «Обновить» результат помечается устаревшим |

## 3. Термины

| Термин | Определение |
|---|---|
| Портфель | Все выбранные на «Поиске» незавершённые эпики. Моделируются вместе, потому что делят команды |
| Доля потока | Часть недельного потока команды, которая уходит на эпик. Считается по завершённым задачам людей команды (`forecastShare`: последние 8 недель → период активности → всё окно) |
| Разработка готова | Все задачи эпика, кроме заглушек, во всех командах завершены (остаток по командам — как в текущем прогнозе) |
| Задача-заглушка | Задача эпика, обозначающая время отладки и бизнес-теста. Признаки — в настройке «Признаки задач-заглушек» (по умолчанию: `заглушка`, `отладка` в названии) или по решению LLM (А4) |
| Загрузка человека | Оценки его задач в секции спринта (существующий расчёт «По людям»: задачи в спринтах, в работе вне спринта, по плановым датам) |
| Ёмкость человека | Рабочие дни секции по производственному календарю × «Часов в рабочем дне» |
| Перегруз | Загрузка сверх ёмкости в секции |
| Блокировка | Найденная LLM ситуация «люди эпика перегружены другой работой в таких-то спринтах», с уверенностью. Задержка от неё считается кодом из перегруза (А2) |
| Бизнес-тест (БТ) | Статусы из настройки «Статусы бизнес-теста» (по умолчанию «БИЗНЕС ТЕСТ») |
| Приёмка | Путь эпика от первого входа в БТ до статуса «Готово», в рабочих днях, со всеми возвратами на доработку |
| P50 / P85 / P95 | Дата, к которой эпик готов в 50 / 85 / 95% прогонов |

## Функциональные блоки

### А1. Кнопка и результат

**Где.** Пиктограмма ✦ «AI-анализ» напротив эпика:
- «По эпикам» — рядом с 💬 у названия эпика, видна всегда;
- «Эпик — история» — в строке эпика, рядом с 💬.

**Запуск.** Щелчок — анализ эпика (А2–А5). Пока идёт — пиктограмма крутится, повторный щелчок
недоступен. Ошибка (нет ключа, нет истории потока, сбой LLM) — подсказка у пиктограммы с причиной;
прежний результат остаётся.

**Результат** хранится в `aiForecasts` по ключу эпика: дата анализа, P50/P85/P95 конца разработки и
готовности, шанс успеть к сроку исполнения, факторы (А5.1), поправки LLM (А4) с отметками
пользователя, текст объяснения.

**Устаревание.** После «Обновить» результат помечается устаревшим: пиктограмма с точкой, отметки на
Ганте бледнее, в подсказке — «анализ от 12.10, данные с тех пор обновлены».

**Карточка эпика** (по «+») — блок «AI-анализ»:
- готовность: P50 / P85 / **P95**; разработка: P50 / P85 / P95; шанс успеть к сроку;
- объяснение и факторы (А5);
- поправки LLM списком, у каждой — «Не учитывать»;
- «Пересчитать» — заново только расчёт, с текущими данными и отметками, **без запроса к LLM**;
- «Новый анализ» — с запросом к LLM.

**Приёмка А1:**
- без ключа API кнопка открывает подсказку «Укажите ключ в Настройках → AI», запроса нет;
- результат переживает перезагрузку страницы;
- «Пересчитать» не делает ни одного запроса к LLM;
- после «Обновить» у проанализированного эпика появляется пометка «устарело».

### А2. Прогноз портфеля (код)

Расширение текущего прогноза (`forecastDelivery` / `forecastForTeams`): вместо одного эпика с
постоянной долей — все эпики портфеля в одном прогоне, неделя за неделей.

**Входы** — те же, что у текущего прогноза, для каждого эпика портфеля:
- остаток задач по командам **без заглушек** (делится по вкладу команд в эпик, как сейчас);
- доля потока эпика в команде (`forecastShare`);
- недельный поток команды за окно истории **без заглушек** (для этого в историю потока сохраняется
  название задачи — сейчас оно не хранится).

Эпик без истории потока ни в одной команде в прогоне не участвует (как сейчас — «нет истории»).

**Прогон** (10 000 прогонов, зерно — как сейчас, `seededRandom`):
1. Каждую неделю каждой команде выбирается неделя её истории (с возвратом) — **одна на команду**:
   эпики команды делят одну и ту же неделю.
2. Поток недели приводится к рабочим дням: история — на одну рабочую неделю
   (`задач × 5 / рабочих дней той недели`), будущая неделя — обратно, по её рабочим дням (А8).
   Новогодняя неделя даёт меньше, полная — как обычно.
3. Эпик получает свою долю недели в каждой своей команде и уменьшает остаток.
4. **Освобождение.** Когда эпик закончил свою часть в команде, его доля в этой команде делится между
   ещё не закончившими эпиками портфеля этой команды пропорционально их долям. Остальная работа
   команды (вне портфеля) не меняется.
5. Разработка эпика готова в неделю, когда он закончил во всех своих командах.
6. **Блокировки** (А4). В доле прогонов, равной уверенности LLM, конец разработки анализируемого эпика
   сдвигается на задержку блокировки. Задержку считает код: перегруз указанных людей в указанных
   секциях, вызванный эпиком-блокером (или прочей работой, если блокер — не эпик портфеля), в часах,
   делённый на рабочую неделю человека (`5 × «Часов в рабочем дне»`). Если людей несколько — берётся
   наибольшая задержка: они работают параллельно. Несколько блокировок суммируются.
7. **Бизнес-тест.** К концу разработки прибавляется приёмка (А3) в рабочих днях по календарю;
   дни отсутствия заказчика (А4) рабочими для приёмки не считаются.
8. Готовность = конец разработки + приёмка.

Эпик, который уже в БТ, разработку не моделирует: приёмка считается от даты входа в БТ (А3).

**Выход для анализируемого эпика:** P50/P85/P95 конца разработки и готовности, шанс успеть к сроку
исполнения (доля прогонов, где готовность не позже срока), узкое место — команда, закончившая
последней (как сейчас), и данные для факторов (А5.1).

**Влияние других эпиков — отдельно.** Для объяснения тот же расчёт повторяется дважды по 5000
прогонов: (а) без освобождения и без блокировок — как сейчас, эпик сам по себе; (б) с освобождением,
без блокировок. Разница даёт вклад освобождения и вклад блокировок в P95.

Считается в `forecast.worker.js`, страница не замирает.

**Приёмка А2** (селфтест на заданной истории потока и с фиксированным зерном):
- эпик без других эпиков в портфеле и без заглушек — тот же P95 разработки, что у текущего прогноза;
- два эпика в одной команде: когда первый закончил, второй ускоряется (P95 раньше, чем без
  освобождения);
- заглушки не уменьшают остаток разработки и не попадают в поток истории;
- блокировка с уверенностью 0,3 срабатывает в 30 ± 2% прогонов;
- перегруз 16 ч при 8-часовом дне — задержка 0,4 недели; двое перегруженных параллельно — берётся
  наибольшая задержка;
- неделя с 3 рабочими днями даёт 3/5 потока;
- P95 готовности не раньше P95 разработки.

### А3. Бизнес-тест: срок заказчика (код)

**Данные.** Один запрос раз в сутки (кэш в `meta`):
`issuetype = Epic AND status WAS IN (<статусы БТ>) AND updated >= -540d` с историей изменений
(`expand=changelog`). Глубина — настройка «История приёмок, мес.» (по умолчанию 18).

**Приёмка эпика** из истории статусов: от первого входа в БТ до первого перехода в «Готово» после
него; рабочие дни — по календарю (А8). Эпики, которые сейчас в БТ, — незавершённые приёмки (в
статистику не идут, но нужны для «уже в БТ»).

**Заказчик** — постановщик эпика (поле из настройки «Постановщик эпика»). Сравнение — по
нормализованному имени (`team.normName`).

**Распределение срока приёмки** для анализируемого эпика:
- приёмки его заказчика (`n` штук) смешиваются с приёмками всех заказчиков с весом `n / (n + 3)`:
  при 1 приёмке своя история весит 25%, при 9 — 75%; без своих — только общие, с пометкой в
  объяснении;
- в прогоне срок выбирается из смеси (с возвратом) и умножается на поправку LLM (А4);
- **эпик уже в БТ** (прошло `e` рабочих дней): срок выбирается только из приёмок длиннее `e`, к дате
  входа прибавляется выбранный срок. Если таких нет — 5 рабочих дней от сегодня и пометка «дольше
  любой прошлой приёмки».

**План менеджера по заглушкам.** Задачи-заглушки эпика, стоящие в спринтах, дают окно, которое
менеджер отвёл на отладку и бизнес-тест: от начала самой ранней до конца самой поздней их секции.
Окно и сумма оценок заглушек передаются LLM (А4) и попадают в объяснение рядом с обычным сроком
приёмки заказчика. В расчёт само окно не подставляется: срок — по истории заказчика с поправкой LLM.

Для объяснения: число приёмок заказчика, медиана и 95% срока, доля приёмок с возвратом (был выход
из БТ не в «Готово»), окно заглушек.

**Приёмка А3** (селфтест на собранной вручную истории изменений):
- одна приёмка; приёмка с возвратом и повторным входом; эпик сейчас в БТ; статус «Бизнес тест» в
  другом регистре распознаётся; статус не из настройки — нет;
- смешивание при `n = 0, 1, 9`;
- «уже в БТ»: выбранный срок всегда больше прошедшего;
- окно заглушек — от начала первой до конца последней их секции.

### А4. Поправки LLM

Один запрос при «Новом анализе». **На входе** (JSON):
- анализируемый эпик: ключ, название, описание (до 3000 символов), статус, срок;
- его задачи: ключ, название, статус, исполнитель, оценка, секция спринта, признак «заглушка по
  настройке»;
- истории эпика (ключ, название, статус);
- последние 30 комментариев эпика и его историй (автор, дата, текст до 500 символов) — читаются из Jira
  при запуске анализа;
- **загрузка людей эпика** — по каждому исполнителю задач эпика и каждой из ближайших секций
  (`personLoad`, сколько секций — как на «По людям»): ёмкость по календарю, загрузка всего, разбивка по
  эпикам (этот эпик / другие эпики портфеля с ключами / прочая работа), перегруз. Для разбивки
  `personLoad` дополнительно отдаёт суммы по эпикам;
- заказчик и его статистика приёмок (А3) — готовыми числами, окно заглушек;
- другие эпики портфеля: ключ, название, статус, общие с эпиком люди;
- сегодня и праздники ближайших 6 месяцев.

**На выходе** (JSON, формат задан в промпте, ответ в режиме JSON):

| Поле | Значение | Как используется |
|---|---|---|
| `blockers` | Блокировки: эпик-блокер из портфеля или `null` (прочая работа), люди, секции, уверенность 0…1, причина («Иванов — единственный backend эпика, в спринтах 25–26 загружен задачами EP-7 на 140%») | Задержка по перегрузу этих людей в этих секциях (А2, шаг 6) в доле прогонов, равной уверенности |
| `stub_tasks` | Задачи эпика, которые тоже являются заглушками, хотя под признаки настройки не попали («Поддержка приёмки», «Сопровождение БТ»), с причиной | Вместе с заглушками по признакам — вне остатка разработки |
| `bt_factor` | Коэффициент к сроку приёмки, обрезается в 0,5…2,0 | Умножает выбранный срок приёмки в каждом прогоне |
| `bt_factor_reason` | Почему: «по комментариям заказчик заранее просит доработки», «эпик крупнее обычных у заказчика», «окно заглушек вдвое короче обычной приёмки заказчика» | В объяснение |
| `customer_absence` | Периоды отсутствия заказчика: с, по, причина, уверенность | Учитываются при уверенности ≥ 0,6: дни не рабочие для приёмки |
| `notes` | До 3 наблюдений, которые не влияют на расчёт, но важны | В объяснение |

**Проверка ответа кодом:** JSON по схеме, значения в границах, даты разбираются; эпик-блокер есть в
портфеле, люди — среди исполнителей задач эпика, секции — из переданных; задачи-заглушки — открытые
задачи этого эпика. Не прошло — один повторный запрос с указанием ошибки; снова не прошло — анализ без
поправок LLM (коэффициент 1, без блокировок, отсутствия и дополнительных заглушек) с пометкой в
объяснении.

**Без LLM** («Пересчитать» при пустых поправках, этап 1): заглушки — только по признакам настройки,
блокировок нет, в объяснении — «блокировки не оценивались».

**Отметки пользователя.** «Не учитывать» у поправки сохраняется в `aiForecasts` и действует при
«Пересчитать» и при следующих «Новых анализах» (отключённая блокировка или заглушка не учитывается,
даже если LLM предложит её снова).

**Приёмка А4:**
- `bt_factor: 5` превращается в 2,0; блокировка с человеком не из исполнителей эпика отбрасывается;
  «заглушка» из чужого эпика отбрасывается;
- неразбираемый ответ дважды — анализ завершается без поправок, с пометкой;
- отключённая блокировка не участвует в «Пересчитать».

### А5. Объяснение срока

**А5.1. Факторы** (код, из расчёта А2–А4):
1. **Остаток** — задач разработки всего и по командам; сколько задач-заглушек вынесено в бизнес-тест.
2. **Доля потока** — по каждой команде: доля эпика, кто из людей команды закрывал задачи эпика за
   последние 8 недель, темп команды (медиана задач в неделю).
3. **Узкое место** — команда, закончившая последней, и в какой доле прогонов.
4. **Влияние других эпиков** — сколько недель к P95 дало освобождение команд (эпики, которые
   закончатся раньше) и сколько отняли блокировки; по каждой блокировке — люди, секции, перегруз в
   часах, задержка и доля прогонов.
5. **Бизнес-тест** — заказчик, его приёмок, медиана и 95% срока, доля возвратов, окно заглушек,
   поправка LLM и её причина, отсутствие заказчика.
6. **Календарь** — праздники в окне прогноза и сколько рабочих дней они забрали.
7. **Разброс** — P50 → P95: насколько неопределённость отодвигает срок.

**А5.2. Текст.** Второй запрос к LLM — после расчёта: по факторам написать 3–5 предложений, почему
P95 именно такой, начиная с главной причины. Каждое число и дата в тексте должны найтись в факторах;
нашлось лишнее — один повтор, затем показывается шаблонный текст из факторов (без LLM). Без LLM
(«Пересчитать») — шаблонный текст.

**А5.3. Где.** Наведение на отметку P95 на Ганте (А6) или на P95 в карточке — подсказка: текст,
затем факторы списком, внизу дата анализа.

**Приёмка А5:**
- число, которого нет в факторах, в подсказку не попадает;
- без LLM подсказка всё равно есть — из шаблона;
- сумма вкладов «освобождение + блокировки» равна разнице P95 с влиянием и без (с точностью до дня).

### А6. Гант: срок и бизнес-тест

На «По эпикам» и «Эпик — история», в строке проанализированного эпика:
- **отметка P95 готовности** — вертикальная линия с флажком «95% · 26.12» (своим цветом, отличным от
  срока исполнения ◆ и планового ◇). Привязка даты к секции — как у срока (`gantt.dueInfo`). Дата за
  шкалой — флажок у края со стрелкой;
- **жёлтая штриховка — бизнес-тест**: от P95 конца разработки до P95 готовности. Эпик уже в БТ —
  от даты входа в БТ; прошедшая часть — гуще, предстоящая — реже;
- штриховка **может перекрывать задачи-заглушки**: секции, где стоят заглушки, — это и есть время
  бизнес-теста, поэтому штриховка ложится поверх их отрезков, отрезки остаются видны;
- в списке задач (по щелчку на полосу) заглушка помечена «заглушка БТ» с подсказкой, откуда признак:
  настройка или LLM;
- наведение на отметку или штриховку — объяснение (А5.3);
- устаревший анализ — отметка и штриховка бледнее.

Отметка видна в светлой и тёмной теме и не перекрывает отметку срока исполнения: при совпадении дат
флажки сдвигаются.

**Приёмка А6:**
- эпик с P95 разработки 05.12 и P95 готовности 26.12 — штриховка от 05.12 до 26.12, флажок на 26.12;
- заглушка в секции, попадающей в окно 05.12–26.12, — под штриховкой, с видимым отрезком и пометкой
  в списке;
- эпик в БТ с 01.10 — штриховка от 01.10, до сегодня гуще;
- без анализа — ни отметки, ни штриховки.

### А7. Подключение LLM

«Настройки → AI»:
- провайдер: ChatGPT (OpenAI) / DeepSeek;
- ключ API — у каждого провайдера свой, хранится в `chrome.storage.local`, в экспорт конфигурации не
  попадает;
- модель — поле с значением по умолчанию (`gpt-5-nano` / `deepseek-v4-flash`), можно сменить;
- «Проверить» — короткий запрос, ответ «связь есть» или ошибка провайдера;
- «Статусы бизнес-теста» (по умолчанию «БИЗНЕС ТЕСТ»), «Признаки задач-заглушек» (по умолчанию
  `заглушка, отладка`), «История приёмок, мес.» (18).

Запросы — `POST` в формате Chat Completions: `https://api.openai.com/v1/chat/completions` или
`https://api.deepseek.com/chat/completions`, ответ в режиме JSON (`response_format: json_object`).
Разрешение на домен провайдера запрашивается при сохранении ключа, как для Jira. Повтор при 429/5xx —
один, через 2 секунды.

### А8. Производственный календарь

**Источник** — репозиторий [d10xa/holidays-calendar](https://github.com/d10xa/holidays-calendar),
один файл на все годы (сейчас 2011–2027):
`https://raw.githubusercontent.com/d10xa/holidays-calendar/master/json/calendar.json`.

Формат: `holidays` — все нерабочие дни (выходные и праздники, с учётом переносов), `preholidays` —
сокращённые предпраздничные, `nowork` — нерабочие дни по отдельным указам. **Рабочий день** — дата,
которой нет ни в `holidays`, ни в `nowork`; сокращённый день считается рабочим. Перенесённая рабочая
суббота в `holidays` не входит — значит, рабочая.

«Настройки → Производственный календарь»:
- файл загружается при первом расчёте и обновляется раз в неделю; хранится в `meta` (`calendar`);
  разрешение на `raw.githubusercontent.com` запрашивается при первой загрузке;
- строка состояния: «Загружен 01.10, годы 2011–2027» и кнопка «Обновить»;
- **ручные правки** — список дат с отметкой «рабочий» / «нерабочий» (корпоративные дни), поверх
  файла;
- нужного года в файле нет или файл не загрузился — для этого года пн–пт, в настройках и в объяснении
  пометка «календарь на 2028 год не опубликован».

Календарь нужен:
- А2 — рабочие дни недели для потока;
- А3 — длительность приёмок;
- А4 — ёмкость людей в секциях (рабочие дни секции × «Часов в рабочем дне») и праздники для LLM.
  Этой же ёмкостью пользуется перегруз на «По людям» — вместо фиксированной «Длительности спринта»,
  когда календарь загружен.

**Приёмка А8:**
- разбор образца `calendar.json`: 2026-01-05 — нерабочий, 2026-01-12 — рабочий, рабочая суббота
  (не в `holidays`) — рабочая, `preholidays` — рабочий;
- года нет в файле — пн–пт и пометка;
- ручная правка «нерабочий» убирает день из рабочих в расчёте;
- спринт с двумя праздниками — ёмкость человека на 16 часов меньше при 8-часовом дне.

## 4. Нефункциональные требования

- **Архитектура.** Расчёт портфеля, приёмки, календарь, признаки заглушек, проверка ответа LLM и
  факторы — модули без интерфейса (`src/js/`), их проверяет селфтест. Клиент LLM и промпты —
  `src/llm/`, грузится по требованию. Новые данные — в общей базе (`src/js/db.js`).
- **Скорость.** Анализ эпика при портфеле из 50 эпиков — расчёт до 5 секунд в фоновом потоке, плюс
  два запроса к LLM. Интерфейс не замирает.
- **Надёжность.** Сбой LLM не мешает расчёту: срок строится без поправок, объяснение — по шаблону.
  Календарь не загрузился — пн–пт с пометкой.
- **Язык.** Тексты интерфейса — в словаре ru/en; объяснение — на языке интерфейса.
- **Тесты.** Селфтест: А2–А6, А8 (приёмки перечислены в блоках); LLM подменяется заглушкой `fetch`.
- **Документация.** README, release notes, раздел «Как читать AI-срок».

## 5. Вне рамок

- Статус-отчёт и риски из переписки (прошлая редакция ТЗ) — отдельными ТЗ после этого.
- AI-срок в «Сводке» и в цвете эпика: «Сводка» пока считает по текущему прогнозу разработки.
- Рост объёма эпика по ходу работы: остаток берётся как есть.
- Ёмкость команды на доработки после возврата из БТ: возвраты уже входят в длительность приёмки.
- Приоритеты между эпиками: освобождённая доля делится пропорционально, без учёта приоритета.
- Эпики без истории потока не получают освобождённую долю.
- Блокировки, найденные для других эпиков портфеля: LLM оценивает только анализируемый эпик.
- Приёмки задач (не эпиков) в статистике заказчика.
- Автоматический анализ по расписанию, лимиты расходов, журнал запросов к LLM.
