# Модель хранения данных

Задача: держать в IndexedDB историю по десяткам тысяч задач так, чтобы это
занимало мегабайты, а не сотни мегабайт, и при этом позволяло пересчитывать
Control Chart на лету при смене фильтров.

## Что вообще нужно хранить

Control Chart строится по одному-единственному факту: **когда задача была в
каком статусе**. Всё остальное (описания, комментарии, вложения, поля) для
графика бесполезно. Поэтому из ответа Jira мы забираем только:

* историю переходов по статусам (`changelog` → items с `field = "status"`);
* момент создания задачи;
* пару атрибутов для фильтров: тип, проект, приоритет, исполнитель;
* (опционально) заголовок — только чтобы подписать точку на графике.

Сырой ответ Jira на одну задачу с `expand=changelog` — это 3–10 КБ JSON.
Наша запись — 100–250 байт.

## Четыре приёма экономии

### 1. Время — целые минуты, а не строки

ISO-строка `"2025-02-06T18:00:00.000+0000"` — 28 символов (в JS-строке 56 байт).
Вместо неё храним число минут от 2000-01-01 UTC:

```
2025-02-06T18:00 → 13 350 720
```

Минутной точности для цикла в днях хватает с запасом, число влезает в Int32
(диапазон — до 4083 года). Экономия: **8 байт вместо 56**, плюс не нужно
парсить строки при каждом пересчёте графика.

### 2. Повторяющиеся строки — в словари

Имена статусов, типов задач, проектов, приоритетов, исполнителей повторяются у
каждой задачи. Они вынесены в отдельный стор `ccDicts`: словарь — это просто
массив строк, а в записи задачи лежит его индекс.

```
dicts: { n: 'type', a: ['Bug', 'Task', 'Story'] }
задача: { ty: 0 }   // Bug
```

10 000 задач × «In Progress» = 220 КБ строк → 10 000 маленьких чисел + один
массив из десятка строк.

Словарь статусов (`StatusDict`) чуть богаче: он помнит ещё id статуса в Jira и
его категорию (`new` / `indeterminate` / `done`) — по категории определяется,
какие колонки считать завершающими.

### 3. История статусов — varint-поток в `Uint8Array`

Самая объёмная часть. В JSON один переход выглядит так:

```json
{ "created": "2025-02-05T15:00:00.000+0000",
  "items": [{ "field": "status", "from": "3", "fromString": "In Progress",
              "to": "10001", "toString": "In Review" }] }
```

Это ~180 байт. Нам же нужны два числа: *когда* и *в какой статус*.
Храним их как поток LEB128-varint'ов:

```
[ Δмин, статус ][ Δмин, статус ][ Δмин, статус ]…
```

* `Δмин` — разница с предыдущим переходом (а не абсолютное время): задачи живут
  днями, а не годами, поэтому дельта обычно укладывается в 1–3 байта;
* `статус` — код из словаря, почти всегда 1 байт;
* первый элемент — момент создания задачи (дельта считается от `c` записи).

Итого **2–4 байта на переход** вместо ~180. Типичная задача с 4–6 переходами —
это 11–20 байт истории.

`Uint8Array` кладётся в IndexedDB как есть: structured clone хранит типизованные
массивы бинарно, без JSON-сериализации.

### 4. Ничего лишнего и короткие имена полей

Имена ключей в IndexedDB хранятся у **каждой** записи, поэтому они однобуквенные
(`c`, `dn`, `tr`). Опциональные поля (`su`, `as`, `lb`, `sp`, `es`) просто
отсутствуют, если данных нет или пользователь отключил их в настройках —
отсутствующее поле не стоит ничего. По умолчанию заголовки хранятся целиком
(до 255 символов — предел Jira) и метки тоже: база общая для всех инструментов
плагина, и анализ по ней должен видеть задачу полностью.

## Схема базы

База **одна на весь плагин** — `jiragantt` (IndexedDB), та же, что у Ганта. Данные
Control Chart лежат в своих сторах с префиксом `cc`, схема и версия описаны в
одном месте — `src/js/db.js` (сторы Control Chart появились в версии 9). Так всё,
что плагин знает о Jira, — эпики и задачи Ганта, доски и история статусов
Control Chart, таблица людей — доступно одним открытием базы.

| Стор | Ключ | Индексы | Содержимое |
|---|---|---|---|
| `ccBoards` | `id` | — | доски: имя, тип, колонки, состояние синхронизации |
| `ccDicts` | `n` | — | словари строк (`status`, `project`, `type`, `priority`, `user`, `label`) |
| `ccIssues` | `['b','i']` | `by_board` → `b`, `by_board_done` → `['b','dn']` | задачи |

Рядом — сторы Ганта (`epics`, `issues`, `sprints`, `people`, …). Общий с Control
Chart из них один: **`people`** — таблица людей («Команда»), ключ — нормализованное
имя. Исполнитель Control Chart (`ccDicts.user`) сопоставляется с профилем по тому
же нормализованному имени: так Control Chart видит команду, роль и статус человека,
а «Команда» — людей с досок Control Chart.

Чистка раздельная: «Очистить базу» и импорт конфигурации Ганта сторы `cc*` не
трогают, «Хранилище» Control Chart чистит только их. Настройки Control Chart — в
`chrome.storage.local` под ключом `cc`; подключение к Jira и язык — общие, из
настроек Ганта (ключ `settings`).

### Запись задачи

| Поле | Тип | Обяз. | Описание |
|---|---|:--:|---|
| `b` | number | да | id доски (часть составного ключа) |
| `i` | number | да | id задачи в Jira (часть составного ключа) |
| `k` | number | да | числовая часть ключа: `ABC-42` → `42` |
| `pj` | number | да | код проекта в словаре `project` (префикс `ABC`) |
| `ty` | number | да | код типа задачи |
| `pr` | number | да | код приоритета |
| `c` | number | да | создана, минут от эпохи |
| `u` | number | да | обновлена — водяной знак для инкрементальной выгрузки |
| `r` | number | да | `resolutiondate` или `-1` |
| `s` | number | да | текущий статус (код) |
| `dn` | number | да | вход в финальный «готовый» участок или `-1`; поле индексируется |
| `tr` | Uint8Array | да | упакованная история статусов |
| `su` | string | нет | заголовок, обрезанный до `summaryMaxLen` (по умолчанию 255 — целиком) |
| `as` | number | нет | код исполнителя |
| `lb` | number[] | нет | коды меток |
| `sp` | number | нет | Story Points |
| `es` | number | нет | исходная оценка, минут |

Составной ключ `['b','i']` даёт идемпотентность: повторная выгрузка той же
задачи перезаписывает запись, а не плодит дубли. Задача, попавшая на две доски,
хранится дважды — это осознанный размен: расчёт по доске становится одним
запросом по индексу `by_board`, без join'ов.

### Запись доски

```js
{
  id: 42,
  name: 'ABC board',
  type: 'scrum',
  projectKey: 'ABC',
  filterId: 10200,
  columns: [ { name: 'In Progress', st: [3, 7] }, … ],  // st — коды статусов
  estimationField: 'customfield_10004',
  lastSyncMin: 13350720,   // водяной знак для инкрементальной выгрузки
  syncedAt: 1739000000000,
  issueCount: 8123
}
```

Колонки берутся из `/rest/agile/1.0/board/{id}/configuration` — именно они
предлагаются в интерфейсе как «колонки цикла» и «колонки Готово».

## Сколько это занимает

Расчётный размер полезной нагрузки (`tests/test.html`, раздел «Оценка размера
хранения») на задаче с четырьмя переходами:

| | На задачу |
|---|---|
| Сырой JSON Jira (урезанный набор полей + changelog) | ~890 Б |
| Наша запись | ~210 Б |
| В том числе история статусов | ~11 Б |

Замер того, что реально просит IndexedDB (Chrome 140, `navigator.storage.estimate`
до и после вставки 5000 записей) — сюда входят накладные расходы стора и записи
индексов:

| Что храним | На задачу | 5000 задач | 10 000 задач |
|---|---|---|---|
| Полная запись (с заголовком и исполнителем) | ~485 Б | 2,4 МБ | ~4,7 МБ |
| Без заголовков (`su`) | ~285 Б | 1,4 МБ | ~2,8 МБ |

То есть заголовок задачи — примерно 40% объёма базы (строки IndexedDB хранит в
UTF-16), поэтому в настройках его можно не сохранять, а в диалоге «Хранилище» —
удалить у уже выгруженных задач.

Для сравнения: полный ответ Jira по одной задаче с историей — 3–10 КБ, то есть
наивное «сложим как пришло» дало бы на тех же 10 000 задачах 30–100 МБ.

Чтение всей доски (5000 записей по индексу `by_board`) занимает ~45 мс, поэтому
пересчёт графика при смене фильтров идёт целиком в памяти, без обращений к Jira.

Квота IndexedDB в Chrome — обычно до 60% свободного места на диске; расширение
дополнительно объявляет `unlimitedStorage`, так что упереться в лимит на
реалистичных объёмах невозможно.

## Инкрементальная выгрузка

При каждой синхронизации в доску пишется `lastSyncMin`. Следующий запуск
добавляет к JQL доски условие `updated >= "<lastSyncMin − 24 ч>"` — сутки запаса
на расхождение таймзон Jira и браузера. Перезапись по составному ключу делает
повтор безопасным. Кнопка «Полная выгрузка» игнорирует водяной знак и
перечитывает историю доски заново.

Сортировка страниц — `ORDER BY created ASC`: дата создания не меняется, поэтому
пагинация не «съезжает», даже если во время выгрузки кто-то правит задачи.
