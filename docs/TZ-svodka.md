# ТЗ: «Сводка» — статус проектов после каждого обновления

Плагин Jira OhMyGant, текущая версия 1.8.0 (выпущены Д1, этап 0 — А1, А2, А3, А5 — и этап 1 — Б0–Б5, Б10).

## 1. Цель

Сейчас, чтобы понять состояние проектов, руководитель смотрит глазами на диаграмму
Ганта и уточняет у коллег. Нужен инструмент, который после каждого обновления данных
сам отвечает на четыре вопроса:

1. Что изменилось с прошлого раза?
2. Какие проекты близки к завершению?
3. Где опаздываем?
4. Где ресурсы используются неэффективно?

И показывает тренд: как состояние проектов менялось во времени.

Отдельно ТЗ включает доработку диаграмм, не связанную со сводкой: задачи канбан-команд
(блок Д1).

## 2. Принятые решения

| Вопрос | Решение |
|---|---|
| Где работает | Внутри плагина, новая вкладка «Сводка». Данные не покидают браузер |
| Как считаются сигналы | Детерминированными правилами. LLM не используется |
| От какого срока считаем опоздание | Только **срок исполнения** (Due date) — обещание заказчику. Плановое завершение в сводке не участвует |
| База для «что изменилось» | С момента последнего просмотра сводки. Переключатель «за 7 дней» |
| Сводка по людям | Только люди в перегрузе. Остальное — на уровне команд |
| Главная мера опоздания | **Запас до срока** в неделях. Шанс успеть — вспомогательное число |
| По каким командам прогноз | По всем командам эпика. Выбор команд в карточке эпика — ручной сценарий «что если», в сводку не попадает |
| Загрузка людей | Везде по остатку (Remaining estimate, при пустом — Original), как на вкладке «По людям» |
| Где живут расчёты | В отдельном модуле без интерфейса: карточка эпика, список, сводка и восстановление истории вызывают одни и те же функции |
| Тренды с первого дня | История восстанавливается задним числом (блок Б3) |
| Автообновление | Догоняющее: Jira доступна только через VPN, поэтому не «ровно в 9:00», а «один раз за рабочий день, как только Jira доступна» |
| Отправка наружу (Telegram, почта) | Не делаем. Только копирование отчёта в буфер обмена |
| Канбан-задачи (Д1) | Работой вне спринта считается вся категория Jira «В работе», кроме статусов, готовых по правилу плагина |

## 3. Термины

| Термин | Определение |
|---|---|
| Журнал синхронизаций | Состояние всех эпиков на момент каждой успешной синхронизации. Хранится 30 дней |
| Недельная запись | Состояние эпика на конец недели (последнее состояние недели). Хранится до 104 недель. Бывает настоящей или восстановленной (Б3) |
| База сравнения | Состояние эпиков, с которым сравнивается текущее в блоке «Что изменилось» |
| Прогноз 50% / 85% | Дата, к которой эпик будет готов в 50% / 85% прогонов Монте-Карло (расчёт по потоку команд) |
| Шанс успеть | Доля прогонов, завершившихся не позже срока исполнения |
| Запас до срока | (срок исполнения − прогноз 85%) в неделях, один знак после запятой. Меньше нуля — опаздываем |
| Сигнал | Сработавшее правило: тип, эпик/команда/человек, важность, пояснение в цифрах, ссылка |
| Цвет эпика | Зелёный: шанс ≥ 85%. Жёлтый: 50–85%. Красный: < 50% или срок исполнения прошёл |
| Дата закрытия задачи | Дата завершения (resolutiondate). Если задача готова по статусу, а даты нет (например, On Prod вне категории «Готово») — дата последнего обновления |
| Jira недоступна | Сетевая ошибка или таймаут: нет VPN, нет сети. Отличается от «не авторизован» (Jira отвечает, но сессия истекла) |

Все подсчёты задач исключают типы из настройки «Типы задач, не учитываемые в
подсчётах» (по умолчанию User Story) — так же, как в текущем прогнозе.

## Архитектурная подготовка

### А. Изменения архитектуры

**Назначение.** Текущая архитектура не выдержит сводку: расчёты размазаны по интерфейсу,
синхронизация не атомарна, тяжёлые вычисления блокируют страницу, а с автообновлением
появятся две одновременно работающие копии страницы.

#### А1. Модуль расчётов без интерфейса

Сейчас прогноз, доли и остаток считаются в функциях отрисовки карточки эпика
(`renderEpicFlow`, `drawForecast`), загрузка людей — в `buildPersonLoad`, счётчики эпика —
в `renderStored` (всё в `app.js`, 1773 строки). Правила в этих местах уже расходились
(поле оценки, исключение User Story).

- Новый модуль (например, `analytics.js`) без обращений к DOM и к сети:
  - **состояние эпика**: счётчики (всего / готово / осталось), оценки, повторные переносы,
    прогноз 50% / 85%, шанс успеть, запас, команды и их доли;
  - **загрузка людей и команд** по секциям (по остатку).
- Все входные данные передаются параметрами, включая момент расчёта и генератор
  случайных чисел — так один код работает для текущего состояния и для прошлых недель (Б3).
- Карточка эпика, список «Сохранённые эпики», окно «кто может подменить», вкладка
  «По людям», сводка и восстановление истории вызывают эти функции.

**Приёмка:** для любого эпика числа в карточке, в списке и в сводке совпадают; селфтест
проверяет модуль напрямую, без страницы.

#### А2. Синхронизация одной записью

Сейчас «Скачать» удаляет задачи сразу после выгрузки, затем идут сетевые шаги (чужие
задачи, Tempo, история потока, спринты, доски), и только потом новые задачи записываются.
Сбой сети посередине оставляет базу без задач эпиков. Каждое хранилище пишется отдельной
транзакцией.

- Синхронизация делится на две фазы:
  1. **сбор**: всё выгружается и считается в памяти, база не меняется;
  2. **запись**: все хранилища (задачи, чужие задачи, спринты, доски, Tempo, история
     потока, служебные ключи, журнал синхронизаций, недельные записи) пишутся **одной
     транзакцией IndexedDB**.
- Ошибка на фазе сбора — база остаётся в прежнем состоянии, запись в журнал не делается.
- Удаление пропавших задач (Б0) — часть той же записи. Если запрос ключей не удался,
  ничего не удаляется.
- Ошибки делятся на три вида: **Jira недоступна** (сеть, таймаут), **не авторизован**,
  **прочие**. Для «недоступна» текст подсказывает проверить VPN.
- У запросов к Jira появляется таймаут (по умолчанию 30 с): без VPN запрос иначе может
  висеть больше минуты.

**Приёмка:** обрыв сети на любом шаге сбора оставляет базу и историю без изменений;
при выключенном VPN «Обновить» за ≤ 30 с сообщает «Jira недоступна — проверьте VPN».

#### А3. Тяжёлые расчёты в фоновом потоке

Прогнозы считаются в основном потоке: 50 эпиков по 10 000 прогонов после каждой
синхронизации и около 2 000 прогнозов при восстановлении истории заморозят страницу
на секунды. В худшем случае (маленькая доля эпика) прогон доходит до 260 недель.

- Прогнозы считаются в Web Worker страницы плагина через модуль А1.
- Интерфейс остаётся отзывчивым, прогресс виден в строке статуса.

**Приёмка:** во время восстановления истории вкладки переключаются и прокручиваются
без задержек.

#### А4. Одна синхронизация на все вкладки

Защита от повторного запуска сейчас — переменная внутри страницы. С автообновлением
страница может быть открыта дважды (вкладка пользователя и фоновая).

- Синхронизация выполняется под общим замком (`navigator.locks`).
- Вторая попытка не запускается параллельно: кнопка показывает «Идёт обновление в другой
  вкладке», по окончании обе вкладки перечитывают данные.

**Приёмка:** одновременное нажатие «Обновить» в двух вкладках даёт одну запись журнала.

#### А5. Настройки и служебные отметки

Настройки кэшируются в памяти страницы и не следят за изменениями из других вкладок:
сохранение формы в одной вкладке затирает поля, изменённые другой (например, время
последней синхронизации).

- Страница подписывается на изменения `chrome.storage` и обновляет кэш настроек.
- Отметки сводки (отметка просмотра, «Принято», время последней автосинхронизации)
  хранятся в IndexedDB (`meta`), а не в настройках: они не должны затираться формой
  и не попадают в экспорт конфигурации.

**Приёмка:** синхронизация в фоновой вкладке, затем сохранение настроек в вкладке
пользователя — время последней синхронизации не откатывается.

## Функциональные блоки

### Б0. Подготовка данных

**Назначение.** Без этих доработок сводка будет считать по неполным или устаревшим данным.

| Доработка | Зачем |
|---|---|
| У задач сохраняется **дата создания** (`created`) | Объём эпика в прошлых неделях для восстановления (Б3) |
| У задач сохраняется **число спринтов** из поля Sprint (сейчас список спринтов читается и выбрасывается) | Правило повторных переносов без хранения задач в истории |
| У эпиков сохраняется **дата завершения** (`resolutiondate`) | Проверка точности прогнозов (Б9) |
| Дата закрытия задачи с запасным вариантом (см. термины) | Задачи вроде On Prod иначе навсегда остаются открытыми в истории |
| При «Обновить» — **удаление пропавших задач**: лёгкий запрос ключей задач выбранных эпиков (без полей, пачками); задачи, которых нет в ответе, удаляются в общей записи (А2) | Сейчас «Обновить» только догружает изменённые задачи: вынесенные из эпика и удалённые остаются со старым эпиком и завышают объём и остаток |
| Окно «кто может подменить» считает занятость **по остатку** (через А1) | Сейчас оно считает по полю из настроек, а «По людям» — по остатку: у одного человека две разные загрузки |

Новые поля требуют повышения `ISSUE_SCHEMA` — одна автоматическая полная перезагрузка.

**Приёмка:**
- задача, перенесённая в эпик вне выбора, после «Обновить» исчезает из объёма исходного эпика;
- задача в статусе On Prod без даты завершения получает дату закрытия по последнему обновлению;
- загрузка человека одинакова на «По людям», в окне замены и в сводке.

### Б1. Хранение истории

**Назначение.** Дать плагину память: без неё не с чем сравнивать и нечего рисовать
во времени.

**Модель — одна запись «эпик в момент времени» в двух хранилищах IndexedDB** (повышение
версии БД; существующие хранилища не трогаются):

| Хранилище | Ключ | Что хранит | Срок | Для чего |
|---|---|---|---|---|
| `syncLog` | синхронизация + эпик, индекс по синхронизации | Состояние каждого эпика на каждую успешную синхронизацию | 30 дней | «Что изменилось» (база может быть внутри недели) |
| `epicWeeks` | эпик + понедельник недели | Состояние эпика на конец недели; признак `restored` | 104 недели | Тренды, мини-графики, «Запас тает», точность прогнозов |

Недельная запись текущей недели перезаписывается при каждой синхронизации. Обе записи
делаются в общей транзакции синхронизации (А2).

**Состояние эпика** (считается модулем А1):

| Поле | Источник |
|---|---|
| ключ, название, статус, дата завершения эпика | эпик |
| срок исполнения | эпик |
| задач всего / готово / осталось | задачи эпика без исключённых типов |
| сумма оценок всего / готово | задачи эпика |
| задач с повторным переносом (в 3+ спринтах, не закрыты) | Б0 |
| прогноз 50% и 85% (даты), шанс успеть, запас до срока | Б2 |
| команды эпика: доля потока, кто чаще замыкает | расчёт потока |

Данные по отдельным задачам в историю не пишутся: всё, что нужно правилам, берётся из
текущей выгрузки (Б0) и агрегатов эпика.

**Когда пишется.** После каждой успешной синхронизации («Обновить», «Скачать»,
автообновление). Неудачная синхронизация ничего не пишет.

**Очистка.**
- «Очистить базу» и импорт конфигурации удаляют всю историю.
- «Скачать» историю не удаляет.
- **Удаление эпика из выбора («Сохранить выбор» без него) историю эпика не удаляет** —
  она нужна для трендов и проверки точности (Б9).

**Объём.** ~300 байт на эпик. На 50 эпиков: журнал ~1,5 МБ (30 дней по 3 синхронизации),
недельные записи ~1,5 МБ за 2 года. Итого около 3 МБ.

**Приёмка:**
- после «Обновить» в журнале ровно одна новая запись на эпик, недельная запись текущей
  недели обновлена;
- записи журнала старше 30 дней удаляются, недельные записи остаются;
- после удаления эпика из выбора его недельные записи на месте;
- объём истории не превышает 10 МБ на 50 эпиков за два года.

### Б2. Детерминированный прогноз, шанс успеть и запас

**Назначение.** Прогноз Монте-Карло случаен: на тех же данных два запуска дают сроки,
отличающиеся на неделю. Без детерминизма сводка сообщала бы о несуществующих сдвигах,
а графики дрожали бы.

**Требования:**

- Генератор случайных чисел с **постоянным зерном — ключом эпика**. Прогноз меняется
  только когда меняются данные.
- **Точка отсчёта — понедельник текущей недели**, а не момент расчёта. Обновление
  в понедельник и в пятницу на одинаковых данных даёт одинаковые даты. Если за неделю ничего
  не закрыто, прогноз через неделю сдвинется на неделю — это настоящий сдвиг, а не шум.
- Число прогонов: 10 000 для текущего состояния, 2 000 для восстановленных недель (Б3).
- Из тех же прогонов считаются:
  - **шанс успеть** — доля прогонов, закончившихся не позже срока исполнения;
  - **запас до срока** — срок исполнения минус прогноз 85%, в неделях.
- Эпик без срока исполнения: шанс и запас не считаются, эпик попадает в блок
  «Качество данных».
- Прогноз по всем командам эпика: остаток делят команды пропорционально вкладу,
  история — период их работы над эпиком, не короче 12 недель.
- Расчёт — модулем А1 в фоновом потоке (А3).

**Приёмка:**
- два пересчёта на одинаковых данных в пределах недели дают одинаковые даты до дня;
- шанс успеть совпадает с долей прогонов, посчитанной вручную на тестовых данных.

### Б3. Восстановление истории задним числом

**Назначение.** Графики тренда, «Запас тает» и «за 7 дней» работают с первого дня, а не
через месяц после запуска. Попутно даёт проверку точности прогнозов (Б9).

**Алгоритм.** Для каждой полной недели W, начиная с более поздней из двух дат —
создание эпика или начало окна истории потока + 5 недель:

1. Объём на неделю W: задачи эпика, созданные до конца W.
2. Остаток на неделю W: из них не закрытые к концу W (по дате закрытия из Б0).
3. Поток команд: история завершений только до начала W.
4. Доли команд: считаются на момент W.
5. Прогноз по Б2 (2 000 прогонов, отсчёт от понедельника W) → недельная запись
   с `restored: true`.

Расчёт — тем же модулем А1, что и текущее состояние, в фоновом потоке (А3).
Недели, у которых истории потока меньше 12 недель, помечаются как ориентировочные.

**Главное правило: настоящие записи не перезаписываются.** Восстанавливаются только
недели, для которых настоящей недельной записи нет.

**Известные ограничения** (указываются в подсказке к восстановленному участку):

- срок исполнения берётся текущий: истории его изменений нет;
- задачи, перенесённые между эпиками или удалённые, учитываются по текущему состоянию;
- состав команд — текущий (Tempo / вкладка «Команда»);
- в истории потока только люди, которые сейчас в командах или есть в выгрузке:
  ушедшие сотрудники не видны, поток прошлых недель может быть занижен;
- глубина — не больше окна истории потока минус 5 недель.

**Когда запускается.** После первой синхронизации с новой версией и после «Скачать»
(дозаполняет пропуски). При «Обновить» не запускается.

**Приёмка:**
- на тестовых данных восстановленный остаток на неделю W совпадает с ручным подсчётом;
- повторный запуск не меняет настоящие недельные записи;
- восстановление 50 эпиков за 52 недели укладывается в 30 секунд без блокировки интерфейса.

### Б4. Правила сигналов

**Назначение.** Превратить данные в короткий список того, что требует внимания.

**Общие требования к сигналу:** тип, объект (эпик / команда / человек), важность
(критично / внимание / информация), текст с цифрами, ссылка (эпик в Jira, выборка JQL
или карточка эпика в плагине). Пороги задаются в настройках (Б10). Правила считаются
по состояниям из модуля А1.

**Какие данные нужны правилу:**
- правила 4.1 сравнивают текущее состояние с базой сравнения (Б5);
- «Запас тает» использует недельные записи, настоящие или восстановленные;
- остальные правила считаются по текущей выгрузке.

#### 4.1. Что изменилось (сравнение с базой)

| Сигнал | Условие | Важность |
|---|---|---|
| Смена статуса эпика | статус отличается от базового | информация |
| Рост объёма | задач +10% или +5 шт., либо оценок +10% | внимание |
| Сокращение объёма | задач −10% или −5 шт. | информация |
| Сдвиг прогноза | прогноз 85% сдвинулся на ≥ 7 дней | позже — внимание, раньше — информация |
| Изменён срок исполнения | дата отличается от базовой | внимание; отметка на графиках |
| Новые повторные переносы | число задач с повторным переносом выросло | внимание |
| Прогресс | закрыто N задач эпика с базы | информация, одной строкой на эпик |
| Эпик добавлен / завершён | появился в выборке / перешёл в «Готово» | информация |

#### 4.2. Близко к завершению

| Сигнал | Условие | Важность |
|---|---|---|
| Близок к финишу | прогноз 85% не дальше 2 недель, или готово ≥ 90% (по оценкам, без оценок — по числу задач) | информация |
| Застрял на финише | готово ≥ 90%, но за 3 недели не закрыто ни одной задачи эпика | внимание |

#### 4.3. Где опаздываем

| Сигнал | Условие | Важность |
|---|---|---|
| Срок исполнения прошёл | срок в прошлом, эпик не завершён | критично |
| Низкий шанс успеть | шанс < 50% | критично |
| Шанс под угрозой | шанс 50–85% | внимание |
| Запас тает | запас снижался 3 недели подряд, даже если он ещё положительный | внимание |
| Застой | эпик в работе, за 3 недели не закрыто ни одной задачи | внимание |
| Хронические переносы | в эпике есть открытые задачи, побывавшие в 3 и более спринтах | внимание |

#### 4.4. Ресурсы

| Сигнал | Условие | Важность |
|---|---|---|
| Перегруз человека | загрузка по остатку > 100% ёмкости в текущей или двух следующих секциях | внимание; **человек называется по имени** |
| Простой рядом с опозданием | у команды загрузка < 50% в двух ближайших секциях, а у жёлтого/красного эпика есть незапланированные задачи (бэклог) людей этой команды | внимание |
| Распыление | на один эпик в работе приходится меньше 2 задач потока команды в неделю. Эпики в работе у команды — все эпики, в которых она закрывала задачи за последние 4 недели (по истории потока, не только сохранённые) | внимание |
| Узкое место | команда замыкает ≥ 50% прогонов в двух и более эпиках | внимание |
| Задачи у уволенных | открытые задачи в текущих/будущих спринтах или бэклоге у людей со статусом «Уволен» | критично |
| Задачи без исполнителя | в текущем спринте есть задачи эпиков без исполнителя | внимание |

Кроме «Перегруза», сигналы о ресурсах говорят о командах, а не о людях.

#### 4.5. Качество данных

Показывается отдельным блоком, всегда. Молчание сводки должно значить «всё хорошо», а не
«нет данных».

| Сигнал | Условие |
|---|---|
| Нет срока исполнения | у эпика пустой Due date — опоздание не оценить |
| Нет оценок | у эпика > 20% задач без оценки |
| Люди без команды | исполнители задач эпиков без команды (Tempo, вкладка «Команда», доска) |
| Мало истории | у команды эпика < 5 полных недель потока — прогноза нет; < 12 — ориентировочный |
| Устаревшие данные | последняя успешная синхронизация старше 3 рабочих дней; если последние попытки автообновления падали с «Jira недоступна» — с подсказкой «проверьте VPN» |
| Ограничения API | последняя проверка доступности API нашла закрытые Agile или Tempo |

**Приёмка:** каждое правило покрыто проверками селфтеста на синтетических данных:
срабатывает на пороге и не срабатывает чуть ниже.

### Б5. Вкладка «Сводка»

**Расположение.** Новая вкладка между «Поиск» и «По эпикам».

**Состав сверху вниз:**

1. **Шапка:** дата последнего обновления; «Сравнение с: <дата базы>»;
   переключатель «с последнего просмотра / за 7 дней»; кнопка «Скопировать отчётом».
   Если данные не обновлялись сегодня из-за недоступности Jira — строка
   «Данные от <дата>: Jira была недоступна, проверьте VPN».
2. **Итог одной строкой:** число эпиков по цветам (зелёный / жёлтый / красный / без срока).
3. **Требует внимания:** до 7 сигналов из всех групп, по важности, затем по величине
   (сколько недель опоздания, на сколько сдвинулся прогноз). Остальные — «показать ещё N».
4. **Блоки** «Что изменилось», «Близко к завершению», «Где опаздываем», «Ресурсы»,
   «Качество данных» — свёрнуты, в заголовке число сигналов.
5. **Таблица портфеля:** эпик, цвет, запас до срока (число + мини-график за 12 недель
   по недельным записям), шанс успеть, прогноз 85%, срок исполнения, готово %.
   Сортировка по запасу, от худшего; эпики без срока — внизу. Клик по строке — графики
   эпика (Б6).

**База сравнения «с последнего просмотра».** Хранится одна **отметка просмотра** —
номер последней синхронизации, которую пользователь видел в сводке (IndexedDB, А5):

- при **открытии** вкладки «Сводка» база показа = текущая отметка, после чего отметка
  сразу становится номером последней синхронизации;
- пока вкладка на экране, после каждой синхронизации отметка сдвигается на новую;
- база показа не меняется, пока вкладка открыта: «Обновить» при открытой сводке
  пересчитывает её относительно той же базы.

Событие ухода со страницы не используется: Chrome может выгрузить вкладку, а запись
в момент закрытия может не завершиться.

Если база старше 30 дней (записи журнала удалены) — берётся самая старая запись журнала,
в шапке пометка.

**«За 7 дней»** — последняя запись журнала не позже 7 дней назад. Если журнала за этот
срок нет (первые дни после запуска) — недельная запись 7 дней назад, в том числе
восстановленная, с пометкой «по восстановленным данным».

**«Принято».** У каждого сигнала кнопка «Принято»: сигнал скрывается, пока его значения
не изменятся сверх порога (например, запас ухудшится ещё на неделю). Отпечаток значений
хранится вместе с отметкой (IndexedDB, А5).

**Пустые состояния:** нет выгрузки → подсказка «Нажмите „Обновить“»; нет базы →
«Сравнивать пока не с чем, изменения появятся после следующего обновления».

**Приёмка:**
- открыть сводку → обновить → изменения показаны относительно прошлого просмотра;
  уйти со вкладки и вернуться без обновления → блок «Что изменилось» пуст;
- после «Обновить» вкладка пересчитывается без перезагрузки страницы;
- «Принято» скрывает сигнал и возвращает его, когда значение ухудшилось сверх порога;
- ссылки открывают правильный эпик / выборку в новой вкладке.

### Б6. Графики тренда

Рисуются собственным SVG, как существующая гистограмма (внешние библиотеки в MV3 не
подключаем). Тёмная тема поддерживается. Источник — недельные записи (Б1, Б3).

**6.1. Портфель: запас до срока во времени.**
- По горизонтали недели, по вертикали запас в неделях. Ноль выделен — это обещание.
- В таблице портфеля — мини-график в строке. Полный график — для выбранных эпиков
  (по умолчанию жёлтые и красные), одна линия на эпик, не больше 8 линий.
- Неделя, в которую изменили срок исполнения, отмечается значком «срок перенесли» —
  чтобы скачок запаса не читался как улучшение.

**6.2. Эпик: как менялся прогноз.**
- По горизонтали неделя, по вертикали прогнозируемая дата завершения.
- Коридор между прогнозом 50% и 85%; прогноз 85% — линия.
- Срок исполнения — ступенчатая линия: перенос срока виден ступенькой.
- Пересечение прогноза и срока выделяется: с этой недели эпик опаздывает.

**6.3. Эпик: сделано против объёма.**
- Две накопительные линии по неделям: задач всего и задач готово.
- Отвечает, почему уезжает срок: растёт объём или падает поток.

**Общие правила:**
- одна точка в неделю — недельная запись;
- восстановленный участок рисуется бледнее, ориентировочные недели — пунктиром;
  в подсказке — ограничения восстановления;
- подсказка на точке: дата, значения, изменения с прошлой точки.

**Приёмка:**
- графики строятся для эпика с восстановленной историей сразу после первой синхронизации;
- перенос срока виден ступенькой на 6.2 и значком на 6.1.

### Б7. Уведомление и отчёт

- **Счётчик на вкладке:** после синхронизации на вкладке «Сводка» число новых сигналов
  важности «внимание» и «критично», не отмеченных «Принято».
- **«Скопировать отчётом»:** текст в буфер обмена, пригодный для мессенджера и почты:
  дата, база сравнения, итог по цветам, список «Требует внимания» со ссылками на эпики.
  Два формата: Markdown и простой текст.

**Приёмка:** отчёт вставляется в Telegram и почту без потери структуры и ссылок.

### Б8. Автообновление: один раз за рабочий день, когда Jira доступна

**Назначение.** Сводка обновляется без нажатия «Обновить».

**Ограничение среды.** Jira доступна только через VPN. В назначенное время VPN может быть
не подключён, отвалиться посреди синхронизации или подключиться позже. Поэтому
обновление не привязано к точному времени: оно **догоняющее** — один раз за рабочий день,
как только Jira стала доступна.

**Логика:**

1. Расписание в настройках: рабочие дни и окно (по умолчанию будни, с 9:00 до 18:00).
   Выключено по умолчанию.
2. `chrome.alarms` в фоновом скрипте срабатывает **каждые 15 минут** и проверяет:
   сегодня рабочий день, время внутри окна, успешной синхронизации сегодня ещё не было.
3. Если проверка пройдена — **проба доступности** прямо в фоновом скрипте: лёгкий запрос
   `<адрес Jira>/status` с таймаутом 5 секунд. Любой HTTP-ответ — Jira доступна.
   Сетевая ошибка или таймаут — нет VPN: **тихо ждём следующей проверки**, вкладку
   не открываем, уведомлений не показываем.
4. Jira доступна — синхронизацию выполняет **страница плагина**, а не фоновый скрипт
   (Chrome усыпляет фоновый скрипт, полная синхронизация может не успеть):
   - если страница открыта — фоновый скрипт посылает ей сообщение «обнови»;
   - если закрыта — открывает её в неактивной вкладке с признаком автозапуска;
     страница синхронизируется и закрывается сама, **если пользователь её не открыл**
     (клик по иконке фокусирует эту же вкладку — тогда она остаётся).
5. Итог синхронизации:
   - **успех** — уведомление «Сводка: N новых сигналов», клик открывает вкладку «Сводка»;
     сегодня больше не запускается;
   - **Jira недоступна** (VPN отвалился посередине) — база не меняется (А2), повтор
     при следующей проверке, без уведомления;
   - **не авторизован** — одно уведомление в день «Войдите в Jira», повторы продолжаются;
   - **прочие ошибки** — одно уведомление в день с текстом ошибки.
6. Если до конца окна обновиться так и не удалось — уведомлений нет; сводка при открытии
   показывает «Данные от <дата>: Jira была недоступна, проверьте VPN» и сигнал
   «Устаревшие данные».
7. Пользователь открыл плагин вручную, расписание включено, сегодня обновления не было,
   Jira доступна — синхронизация запускается сразу.
8. Браузер был закрыт — проверки продолжаются после его запуска по тем же правилам.

- Новые разрешения манифеста: `alarms`, `notifications`.
- Время последней успешной автосинхронизации и последней попытки хранятся в IndexedDB (А5).

**Приёмка:**
- VPN выключен в 9:00 и включён в 10:20 → синхронизация не позже 10:35, до этого ни одной
  открытой вкладки и ни одного уведомления;
- VPN отвалился посреди синхронизации → база не изменилась, успешная синхронизация
  на следующей проверке;
- истекла сессия → одно уведомление за день;
- открытая пользователем вкладка плагина не закрывается.

### Б9. Точность прогнозов

**Назначение.** Проверять, насколько прогнозам можно верить.

- Источник — **недельные записи истории** (Б1, включая восстановленные), а не список
  сохранённых эпиков: история эпика остаётся и после его удаления из выбора.
- Эпик считается завершённым в неделю, когда в его записи впервые появились статус
  «Готово» и дата завершения эпика (Б0). Если даты нет — дата закрытия последней задачи.
- Для каждого завершённого эпика прогнозы из записей за 8, 4 и 2 недели до финиша
  сравниваются с фактической датой.
- Показатель: доля случаев, когда факт уложился в прогноз 85%. Ожидаемое значение около 85%.
  Сильно ниже — прогноз оптимистичен, сильно выше — перестраховывается.
- Раздел в «Сводке», свёрнут: таблица «эпик — прогноз за 8/4/2 недели до финиша — факт —
  попал в 85% или нет» и итоговая доля.
- Ограничение: эпик, удалённый из выбора до завершения, не попадёт в проверку —
  его завершения плагин не увидит.

**Приёмка:** на синтетическом эпике с известной датой завершения показатель считается
правильно; эпик, удалённый из выбора после завершения, остаётся в проверке.

Новая карточка «Сводка» в настройках. Значения по умолчанию:

| Настройка | По умолчанию |
|---|---|
| Порог «шанс успеть»: зелёный / жёлтый | 85% / 50% |
| Значимый сдвиг прогноза | 7 дней |
| Рост / сокращение объёма | ±10% или ±5 задач |
| «Близко к завершению»: прогноз / готово | 2 недели / 90% |

| Спринтов для «повторного переноса» | 3 |
| Недозагрузка для «простоя» | < 50% |

## Доработка вне сводки

### Д1. Задачи вне спринта, находящиеся в работе, — в текущей секции

**Проблема.** Аналитики работают по канбану, без спринтов. Их задачи не привязаны
к спринту, поэтому:

- на обеих диаграммах («По эпикам», «По людям») они попадают в крайнюю правую колонку
  «Бэклог», хотя над ними работают сейчас;
- в загрузке по секциям (перегруз, окно «кто может подменить») их нет: у аналитиков
  всегда пустая текущая секция;
- в строку «Прочие» они не попадают вовсе: задачи людей в чужих эпиках выгружаются
  только из открытых и будущих спринтов.

**Правило размещения.** Задача без спринта, не готовая, со статусом из **категории Jira
«В работе»**, показывается в **секции текущего спринта** — той, что содержит сегодняшний
день (если такой секции нет — в первой секции диаграммы).

| Задача без спринта | Где показывается |
|---|---|
| В работе | Текущая секция (новое) |
| Остальные незавершённые (к выполнению, новая и т. п.) | «Бэклог», как сейчас |
| Готовая | Нигде, как сейчас |

**Какие статусы считаются работой.** Все статусы категории Jira «В работе»
(`statusCategory = indeterminate`): «В работе», «Анализ», «Тест», «Бизнес тест», «Ревью»
и любые нестандартные статусы этой категории. Настройка не нужна: категорию статусу
назначает сама Jira.

Исключение — статусы, которые плагин уже считает готовыми, хотя в Jira они в категории
«В работе» (On Prod, статусы из настройки «Статусы, означающие „Готово“»). Такие задачи
готовы и в текущую секцию не попадают: правило готовности плагина важнее категории.

**Отображение:**

- в ячейке текущей секции такие задачи рисуются отдельным отрезком **«Вне спринта»**
  рядом с отрезками спринтов, нейтральным цветом (у них нет доски, а значит, и цвета
  команды);
- во всплывающем списке задач ячейки у каждой такой задачи — **пиктограмма «вне спринта»**
  с подсказкой: «Задача не в спринте (канбан). Показана в текущей секции, потому что
  в работе»;
- в остальном строка задачи такая же, как у задач спринта: ссылка, статус, исполнитель,
  оценка.

**Подсчёты:**

- итоги ячеек и строк текущей секции включают такие задачи, доля готовых в ячейке
  считается как обычно;
- колонка «Бэклог» и счётчик «невыполненных задач без спринта» их **не** включают:
  одна задача не считается дважды;
- загрузка людей (перегруз на «По людям», окно «кто может подменить», сигнал «Перегруз»
  в сводке) учитывает их в текущей секции по остатку.

Задача с большим остатком (долгая аналитика) целиком ляжет на текущую секцию и может
дать перегруз. Это честно: такова текущая незавершённая работа человека.

**Выгрузка «Прочих».** Запрос задач людей в чужих эпиках расширяется условием
`sprint is EMPTY AND statusCategory = "In Progress"`; из выгруженного отбрасываются
задачи, готовые по правилу плагина. Так канбан-задачи аналитиков в чужих эпиках появляются в строке «Прочие»
в текущей секции.

**Что не меняется:** шкала секций (она строится по спринтам), прогноз сроков и история
потока (считаются по датам завершения, спринт им не важен).

**Где реализуется.** Правило размещения — в построении модели диаграмм и в модуле
расчётов (А1), чтобы загрузка на диаграмме, в окне замены и в сводке совпадала.

**Приёмка:**
- задача аналитика без спринта в статусе «В работе» видна в текущей секции на обеих
  вкладках, в списке задач ячейки — с пиктограммой «вне спринта», в «Бэклоге» её нет;
- задача без спринта в статусе «К выполнению» остаётся в «Бэклоге»;
- задача без спринта в нестандартном статусе категории «В работе» (например, «Анализ»
  или «Ревью») тоже попадает в текущую секцию;
- задача без спринта в статусе On Prod (категория «В работе», но готова по правилу
  плагина) в текущую секцию не попадает;
- канбан-задача аналитика в чужом эпике появляется в строке «Прочие» в текущей секции;
- загрузка аналитика в текущей секции включает такие задачи, одинаково на «По людям»,
  в окне замены и в сводке.

## 4. Нефункциональные требования

- **Приватность.** Данные не покидают браузер. Никаких внешних API, кроме самой Jira.
- **Производительность.** Расчёт сводки после синхронизации ≤ 2 с на 50 эпиков и
  2000 задач, восстановление истории (Б3) ≤ 30 с — **без блокировки интерфейса** (А3),
  с прогрессом в строке статуса. Лёгкий запрос ключей для удаления пропавших задач (Б0) —
  не больше 20 страниц на 2000 задач.
- **Надёжность.** Сбой сети или VPN на любом шаге синхронизации не портит базу
  и историю (А2). Две вкладки плагина не синхронизируются одновременно (А4).
- **Язык.** Все тексты — в словаре ru/en.
- **Тесты.** Селфтест: модуль расчётов А1 напрямую, атомарность записи А2 (обрыв
  на каждом шаге), доработки Б0, каждое правило Б4, детерминизм Б2, восстановление
  и защита настоящих записей Б3, срок хранения Б1, база сравнения Б5, логика
  автообновления Б8 (доступна / недоступна / не авторизован), точность Б9, размещение
  задач вне спринта Д1 (текущая секция, «Бэклог», «Прочие», загрузка без двойного учёта).
- **Документация.** README и INSTALL обновляются вместе с каждым блоком.

## 5. Вне рамок

- LLM и пересказ сводки «человеческим языком».
- Отправка сводки в Telegram, почту и другие внешние сервисы.
- Второй срок (плановое завершение) в расчётах опоздания.
- Рейтинги и сравнения людей, кроме сигнала о перегрузе.
- Выбор команд в карточке эпика как источник для сводки.
- Управление VPN из плагина: плагин только определяет, доступна ли Jira.
- Кумулятивная диаграмма по статусам, сравнение с базовым планом на Ганте,
  пузырьковая матрица «готовность × риск».

## 6. Порядок работ

| Этап | Блоки | Результат |
|---|---|---|
| 0 | А1, А2, А3, А5 | Расчёты в отдельном модуле, атомарная синхронизация, фоновый поток; видимых изменений почти нет, всё существующее работает как раньше |
| 1 | Б0, Б1, Б2, Б3, Б4, Б5 (без «Принято»), Б10 | Вкладка «Сводка» с сигналами и таблицей портфеля; история восстановлена, поэтому мини-графики и «Запас тает» работают сразу |
| 2 | Б6 | Графики тренда: запас, прогноз во времени, сделано против объёма |
| 3 | Б5 «Принято», Б7 | Меньше шума, счётчик, отчёт в буфер обмена |
| 4 | А4, Б8 | Автообновление с учётом VPN и уведомления |
| 5 | Б9 | Проверка точности прогнозов |
| Д | Д1 | Канбан-задачи в текущей секции. Независим от сводки, можно выпустить отдельно в любой момент |

Каждый этап — отдельный релиз с повышением версии. А4 (замок) нужен только с появлением
второй вкладки, поэтому идёт вместе с Б8.

Д1 проще всего сделать сразу, отдельным небольшим релизом: он маленький и сразу полезен.
Если он выйдет раньше этапа 0, его правило для загрузки людей при создании модуля
расчётов (А1) переносится туда вместе с остальной логикой.

## 7. Открытые вопросы

- **Задачи в работе в закрытом спринте.** Спринт закончился, а задача осталась в статусе
  «В работе» и не перенесена в новый спринт. Сейчас такие задачи пропадают с диаграмм
  совсем: их спринт вне шкалы. Логично показывать их по правилу Д1 — в текущей секции,
  с пиктограммой «спринт закрыт». В Д1 не включено, требует решения.
