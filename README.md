# Jira OhMyGant — расширение Chrome

Диаграмма Ганта по спринтам для локальной Jira (Atlassian Jira Server 9.8.0).
Задачи выбранных эпиков скачиваются в локальную базу IndexedDB, диаграмма
строится офлайн из неё — Jira дёргается только при загрузке и обновлении.

Пошаговая инструкция по установке и настройке — в [INSTALL.md](INSTALL.md).

## Установка

1. `chrome://extensions` → включить **Режим разработчика**.
2. **Загрузить распакованное расширение** → указать эту папку.
3. Кликнуть по иконке расширения — откроется отдельная вкладка приложения.

## Первый запуск

Вкладка **Настройки**:

1. **Адрес Jira** — например `https://jira.company.local`.
2. **Разрешить доступ к домену** — расширение просит host-permission на этот
   домен (в манифесте домены не зашиты, только `optional_host_permissions`).
3. **Проверить подключение** — покажет ваше имя из `/rest/api/2/myself`.
4. **Определить поля Jira** — находит id полей `Epic Link`, `Sprint`,
   `Epic Name`, `Story Points`, а также `Planned Start` / `Planned End` (в Jira Server это
   кастомные поля с разными номерами). Плановые даты ищутся по названию поля
   и по его JQL-имени (`clauseNames`): «Planned Start/End», «Target start/end»,
   «Плановое начало/завершение», причём поля типа «дата» в приоритете — в Jira
   бывают одноимённые поля разных типов. Если автоопределение выбрало не то,
   поле можно указать вручную в выпадающих списках «Поле „Плановое начало“» /
   «Поле „Плановое завершение“» (там перечислены все поля типа дата/дата-время)
   и нажать «Обновить данные».
5. **Что считать оценкой** — Original Estimate, Remaining Estimate или Story
   Points. Часы переводятся в дни по значению «Часов в рабочем дне». Настройка
   действует на все вкладки, кроме «По людям»: там считается остаток работы (см.
   ниже).
6. **Доска** — «Загрузить список досок» и выбрать доску: с неё берутся спринты
   и их даты, включая будущие спринты без задач. Без доски спринты собираются
   из полей самих задач.

### Авторизация

Сначала запрос уходит с cookie текущей сессии браузера (вы уже залогинены в
Jira в этом Chrome) — ничего вводить не нужно. Если Jira отвечает 401/403 или
редиректит на форму логина, запрос повторяется с **Personal Access Token** из
настроек (`Authorization: Bearer`). Токен лежит в `chrome.storage.local`.

## Работа

- **Поиск эпиков** — найти эпики по названию или ключам, отметить нужные,
  «Сохранить выбор». В поле поиска можно **вставить сразу несколько ключей** —
  через запятую, пробел или в столбик: они уходят в Jira одним `key in (…) AND
  issuetype = Epic`, а не смешиваются с поиском по названию (ключ вида `PRJ-123`
  в текстовом поиске Jira вытаскивает половину проекта). Если в строке есть и
  ключи, и слова, выполняются оба поиска, результаты объединяются без дублей.
  Ключи, которых не нашлось (не эпик, чужой проект, опечатка), перечисляются
  красной строкой над списком. Задачи выбранных эпиков скачиваются в IndexedDB. В строке
  эпика — статус (лейбл в цветах Jira), четыре даты: создан, плановое начало,
  плановое завершение (поля Planned Start/End) и срок исполнения (Due date), а
  также исполнитель эпика (постановщик — в карточке по «+»); поля берутся по
  умолчанию из стандартных `assignee` / `reporter`, но в «Настройках» можно
  выбрать любое поле типа «пользователь» (например, кастомный «Владелец
  продукта»); **экспресс-оценка** — оценка, внесённая в сам эпик, и **оценка** —
  сумма оценок всех его задач (оценка самого эпика в неё не входит); и **метки** эпика
  (`labels`) чипами в одну строку: первые три видны, остальные за чипом «+N»,
  который открывает всплывашку с ними; у сохранённых эпиков — колонка
  **«Списано»**: затраченное время в днях по ворклогам самого эпика
  (`timespent`) и всех его задач из выгрузки (`aggregatetimespent`, с
  подзадачами), в подсказке — разбивка; колонка **«Готово»** — доля выполнения
  эпика по оценкам: оценки задач в статусах категории «Готово» (Готово, On Prod,
  Cancel) относительно оценок всех задач (без оценок — по количеству), с
  мини-шкалой. В строке из дат оставлены плановое завершение и срок; полная
  карточка эпика (создан, плановое начало, все даты, люди, метки, списано,
  доля) открывается по «+» в начале строки. Метки и имя исполнителя **кликабельны**:
  клик фильтрует оба списка по метке или по исполнителю (фильтры складываются,
  повторный клик снимает), активные фильтры и кнопка «Снять фильтры» — в шапке
  списка;
  подписи колонок — в шапке списка, которая при прокрутке остаётся видимой под
  верхней панелью. Если срок незавершённого эпика наступает в ближайшие 14 дней
  или уже прошёл, вся строка подсвечивается красным, а в подсказке к строке —
  «срок через N дн.» / «срок прошёл N дн. назад». Списки отсортированы по
  статусу и названию, над каждым — сводка по статусам.
- Логотип «Jira OhMyGant»: наведение показывает окно «О плагине» (версия, автор),
  щелчок закрепляет его — оно не пропадает, пока его не закроют повторным щелчком,
  щелчком мимо или Esc. Номер версии — ссылка: открывает release notes
  (`RELEASE_NOTES.md`) в окне.
- Вкладки в шапке: «Поиск» (лупа), «Сводка» (график), затем **ракурсы диаграммы**
  одной группой на общей подложке — «По эпикам» (полосы Ганта), «По людям»
  (человек с полосами) и «Эпик — история» (дерево с полосами), дальше «Команда»
  (группа людей) и «Настройки» (шестерёнка).
- **Ширина колонки названий** на всех ракурсах меняется: потяните правую границу
  заголовка колонки мышью (или стрелками ←/→ на ней), двойной щелчок — ширина по
  умолчанию. Ширина запоминается отдельно для каждого ракурса, подписи эпиков и
  историй растут вместе с колонкой. Подпись
  пиктограммы — во всплывающей подсказке. Справа от вкладок — текущая дата
  (дд.мм.гггг).
- **Обновить данные** — догружает задачи, изменённые с прошлой синхронизации
  (`updated >= …`), включая новые. Спринты при этом перечитываются **всегда**,
  независимо от задач: сначала целиком все доски, встречавшиеся в данных (там
  видны и новые спринты без задач), затем поштучно через `/rest/agile/1.0/sprint/{id}`
  все незакрытые спринты без дат и те, до которых доска не дотянулась. Поэтому
  проставленные в Jira даты будущих спринтов подхватываются уже следующим
  обновлением, даже если ни одна задача не менялась. Если дат в Jira нет вовсе,
  они берутся **из названия спринта** по шаблону `[дд.мм - дд.мм]` (год — из
  названия или текущий, переход через Новый год учитывается). После обновления
  строка статуса показывает сводку: сколько незакрытых спринтов с датами, без
  дат и сколько дат взято из названий; если какую-то доску прочитать не удалось,
  об этом отдельное сообщение (подробности — в консоли страницы).
  Кроме задач целевых эпиков, для каждого их исполнителя загружается снимок
  **всех его задач в текущем и будущих спринтах** вне целевых эпиков (JQL:
  `assignee in (…) AND (sprint in openSprints() OR sprint in futureSprints())
  AND Epic Link not in (…)`) вместе с названиями этих эпиков — так на вкладке
  «По людям» видна полная загрузка человека. Снимок пересобирается при
  каждой синхронизации; если его загрузка не удалась, основная синхронизация
  всё равно завершается, а ошибка показывается отдельно.
  Для ракурса «Эпик — история» синхронизация также сохраняет
  **приоритет** задач и эпиков, **связи** задач и порядок приоритетов Jira
  (`/rest/api/2/priority`). Из **комментариев эпиков и историй** (задачи типов из
  настройки «Типы историй», по умолчанию `User Story, Story, История` — Jira отдаёт
  название типа на языке пользователя) разбираются кодовые слова
  `(omg project) Название` — проект эпика (действует последняя по дате метка) — и
  `(omg comment) текст` — заметки; остальные комментарии в базу не пишутся.
  Комментарии перечитываются только у эпиков и историй, изменившихся с прошлой
  синхронизации (новый комментарий сдвигает «Обновлено»), при «Скачать заново» —
  у всех. Отдельным снимком загружаются **задачи историй из других эпиков** —
  связанные с историей связью из настройки «Связи задачи с историей» (по
  умолчанию `Relates, is subtask of`); эпики и другие истории на том конце связи не в счёт. Если
  комментарии или эти задачи прочитать не удалось, синхронизация завершается, а
  об ошибке сказано отдельно; прежние метки и заметки остаются.
  **Скачать заново** — полная перезагрузка.
  Обе команды — одной кнопкой-пиктограммой ↻ справа в шапке: щелчок — «Обновить»,
  Shift+щелчок — «Скачать заново»; стрелка ▾ рядом открывает меню с обоими
  действиями. Пока идёт выгрузка, значок крутится, кнопка неактивна.
- Над вкладкой «По эпикам» — фильтр по **исполнителю эпика** (выпадающий список с
  количеством эпиков у каждого, пункты «— все —» и «Без исполнителя»);
  диаграмма строится только по подходящим эпикам и их задачам, выбор
  запоминается в настройках. Кроме него на Гант влияет страница «Поиск
  эпиков»: **снятая галочка** у сохранённого эпика сразу скрывает его с
  диаграммы (флаг хранится в базе и переживает перезагрузку и «Обновить
  данные»; «Сохранить выбор» по-прежнему удаляет неотмеченные эпики из базы),
  а **фильтры по метке и исполнителю** применяются к Ганту так же, как к
  списку. Над диаграммой показано, сколько эпиков скрыто галочками и какие
  фильтры пришли со страницы поиска, со ссылкой «снять фильтры».
- **Ручной порядок эпиков** на «По эпикам»: у строки эпика слева от номера — ручка
  ⋮⋮, за неё эпик перетаскивается выше или ниже; линия-указатель показывает, куда
  он встанет. Бросить можно только между эпиками — исполнители едут вместе со своим
  эпиком, раскрытость сохраняется, номера пересчитываются. Без мыши: фокус на ручку
  и **Alt+↑ / Alt+↓**. Пока ничего не перетаскивали — автоматический порядок; после
  первого переноса над диаграммой — «Порядок: вручную» и кнопка **«Сбросить
  порядок»**. Новый эпик встаёт в конец, убранный из выбора выпадает из порядка;
  скрытые галочкой и фильтрами эпики держат своё место. Порядок хранится в плагине
  (IndexedDB), в Jira не пишется (ранг Jira — это порядок бэклога команд) и
  переносится экспортом и импортом конфигурации (`epicOrder`).
- **По эпикам** — эпики (порядок по статусу, лейблы статусов, бэклог, фильтры
  по исполнителю эпика и со страницы поиска), подпись эпика — ключ и **Epic
  Name** (кастомное поле Jira `gh-epic-label`; если оно пустое — название);
  вложенные строки — **исполнители**
  задач эпика (только те, у кого есть задачи в текущем или будущих спринтах
  либо в бэклоге; итоги эпика при этом считаются по всем задачам). Имя человека
  кликабельно: раскрываются все эпики с его участием, остальные сворачиваются,
  его строки подсвечены; над диаграммой — «снять фильтр». Рядом с 💬 у эпика —
  переключатель **⚡ «критический путь»**: подсвечивает оранжевой обводкой полосы
  людей, которые (1) определяют конец эпика — их открытые задачи заканчиваются
  позже всех (без спринтов — самый большой остаток оценок) и/или (2) не
  укладываются в срок эпика — остаток их оценок больше ёмкости в рабочих днях
  до срока (дни × «часов в дне»; нагрузка по другим эпикам не вычитается).
  У имени — ⚡ с причиной, в подсказке переключателя — сводка.
- Обе вкладки открываются **свёрнутыми**: видны только строки эпиков (или людей)
  с итогами, вложенные строки раскрываются стрелкой у названия или кнопкой
  «Развернуть всё». Раскрытое состояние держится, пока открыта вкладка; после
  «Обновить» диаграмма снова сворачивается.
- Общее для **По эпикам** / **По людям** — слева дерево (эпик или исполнитель →
  проекты) с количеством задач и суммой оценок, справа полосы по временным
  секциям с количеством задач и суммой времени в каждой. У эпика полоса-итог
  **жёлтая**, одна на секцию. У человека полоса делится на две части
  пропорционально объёму: слева жёлтая — задачи целевых эпиков, справа серая —
  задачи прочих эпиков (в каждой части — количество и сумма оценок). Вложенные
  строки (проекты и «Прочие») рисуются тонкими **голубыми** отрезками, по одному
  на каждый спринт секции, с названием спринта; команда спринта видна по цветной
  метке в заголовке колонки и в подсказке отрезка. Рядом с названием
  эпика стоит его статус из Jira — лейблом в цветах Jira — и **жёлтый баллон** с
  числом задач не в статусе «Готово» (сколько осталось); эпики отсортированы по
  статусу: сверху «в работе» и «бизнес тест», ниже «сделать» и «new», в самом
  низу «готово». На вкладке по людям исполнители сгруппированы по **командам**
  (строка-заголовок с названием и итогами), внутри команды — по объёму работы, а
  вложенные строки человека — **эпики** (ключ + Epic Name), в которых у него есть
  задачи в текущем или будущих спринтах либо в бэклоге; люди без такой работы на
  вкладке не показываются. Клик по эпику раскрывает всех людей с его задачами,
  остальных сворачивает, его строки подсвечены; над диаграммой — «снять фильтр».
  Числовые метки (количество задач и оценка) на диаграммах не показываются: итоги
  видны в подсказках и в полосах: сначала целевые (отмеченные галочками на
  «Поиске») со светло-жёлтой заливкой, затем прочие эпики отдельными строками;
  задачи без эпика собираются в строку «Без эпика».
  Под проектами человека стоит строка **«Прочие»** — его задачи в эпиках вне
  выбранных (количество и оценка, отрезки по спринтам); те же итоги — серым
  бейджем `+N · оценка` рядом с именем, а в подсказке по человеку — список этих
  эпиков со ссылками. Из профиля вкладки «Команда» подтягиваются роль (зелёный
  лейбл рядом с именем), статус (уволенный — серое имя, аутстаф — жёлтое) и
  информационные системы (в подсказке по человеку). Колонка имён на этой
  вкладке на 20 % шире, чем на вкладке по эпикам. Рядом с именем — пиктограмма
  **⇄ «кто может подменить»** (есть и на «По эпикам»): окно со списком
  коллег с той же ролью и хотя бы одной общей информационной системой (уволенные
  не учитываются), отсортированных по числу общих систем; общие системы
  подсвечены, у аутстафа пометка, отдельно перечислены системы сотрудника, для
  которых замены не нашлось. У каждого кандидата показана **занятость** по трём
  ближайшим секциям (текущая и две следующие): процент от ёмкости спринта
  (длительность спринта × часов в дне), перегрузка выделена красным; в подсказке
  — спринты секции, часы и ёмкость. Нагрузка считается по всей выгрузке, включая
  задачи вне целевых эпиков, и не зависит от фильтров.
  Клик по названию эпика или исполнителя открывает подсказку:
  всего задач, из них в статусе «Готово», из них в прочих статусах, **невыполненных**
  задач без спринта, суммарная оценка и разбивка по проектам. Эпики в дереве и в
  списках на вкладке «Поиск эпиков» пронумерованы по порядку. В подсказке всё
  кликабельно и открывается в новой вкладке: заголовок ведёт на сам эпик
  (`/browse/…`), каждое число и каждая строка проекта — на соответствующую
  выборку задач в Jira (`/issues/?jql=…`). Выборки по «Готово» и «прочим»
  перечисляют реальные названия статусов из загруженных задач, поэтому число в
  подсказке и результат в Jira совпадают. Для исполнителя выборка строится по его
  логину Jira. Ссылки появляются, только если в настройках задан адрес Jira.
- **Команда** — список людей из выгрузки (исполнители задач целевых и прочих
  эпиков) с командой-доской и объёмами; над таблицей — сводка: сколько
  сотрудников и сколько в каждой роли (без уволенных и аутстафа, «без роли»
  отдельно). Для каждого задаются **роль** (Developer, Frontend dev,
  Backend dev, 1C dev, QA, Analytic, Team Lead, Support, Project Manager, DevOps, Sysadm), **информационные системы**
  (несколько; справочник — поле «Информационные системы» в «Настройках») и
  **статус** (штатный сотрудник, аутстаф, уволен). Сохраняется сразу при
  изменении, в отдельное хранилище `people`, которое синхронизация не трогает:
  при каждой выгрузке люди сопоставляются с профилями по имени (без учёта
  регистра, лишних пробелов и «ё»). Профили людей, которых в выгрузке больше
  нет, остаются в конце списка с пометкой — их можно удалить крестиком. Кнопка
  «Очистить базу» профили тоже не удаляет.
- Язык интерфейса (русский/английский) переключается в шапке; все подписи — в
  `src/js/dict.js`.

## Эпик — история

Ракурс для отчёта о статусе «проект → эпик → история» — то, что менеджеры вели в Excel.

- **Проект** — группа эпиков, в Jira её нет. Принадлежность эпика хранится в
  комментарии к эпику `(omg project) Название`; действует последний по дате. Названия
  сравниваются без учёта регистра и лишних пробелов, показывается написание из самой
  свежей метки. Меток нет или последняя пустая — эпик в группе «Без проекта» (внизу).
- **Смена проекта** — кнопка «Проект…» у эпика: существующий проект, новый или «Без
  проекта». Плагин публикует в эпик комментарий `(omg project) …` (Jira разошлёт
  письмо наблюдателям — окно об этом предупреждает) и сразу переносит эпик. Ошибка
  публикации — эпик на месте, сообщение в строке статуса.
- **Переименовать…** у проекта — новая метка публикуется во все эпики проекта из вашей
  выборки (включая скрытые галочкой и фильтрами). Эпики этого проекта в чужих
  выборках плагин не видит — у них останется старое название. Если часть публикаций
  не прошла, переименованные эпики переходят в новый проект, остальные остаются, их
  ключи — в строке статуса.
- **Вид — как таблица статуса.** Слева выровненные колонки: название (проект → эпик →
  история, с пиктограммой приоритета), **«Статус»** (цветная точка и название),
  **«Готово»** (тонкая шкала и «N из M») и **«Срок»** (◆ срок исполнения, ◇ плановое
  завершение; красным — прошёл или ближе 14 дней). Проект — лёгкая подложка на всю
  строку. Справа — полосы, как на классической диаграмме Ганта: у проекта «скобка» с
  уголками на концах, у эпика — сплошной брусок, у истории — тонкая линия с точкой в
  первой секции, где у неё есть работа («Без истории» — линия без точки). Цвет один:
  сделанное — насыщенным синим, остаток — бледным. Цифры «задач · оценка» мелко под
  полосой, спринты — в подсказке. Шапка секций компактная — «Текущий», «+1», «+2» и точки команд; список
  спринтов — по щелчку. Действия строки («Проект…», 💬, ✎ заметка, «Переименовать…») —
  при наведении. Готовые истории эпика свёрнуты в строку «Готовые истории · N».
  Направляющие дерева — тонкие вертикальные линии от стрелки проекта и эпика вниз по
  строкам их блока; при наведении на строку линия её эпика подсвечивается синим.
  Между эпиками разделитель чуть заметнее, чем между историями.
  Свёрнутость, «Развернуть всё» и подсказка по эпику — как на «По эпикам».
- Если ни один тип задач в эпиках не совпал с «Типами историй», над диаграммой —
  подсказка со списком типов задач и кнопкой «Считать историями: …» для похожего типа.
- Если истории есть, но ни у одной нет задач по связи из настройки «Связь задачи с
  историей», над диаграммой — подсказка: какие связи есть у историй в Jira (с
  количеством) и кнопки «Считать связью: …». Задачи из других эпиков по новой связи
  подтянутся после «Обновить».
- **Какие эпики** — как на «По эпикам»: галочки и фильтры «Поиска», фильтр по
  исполнителю эпика.
- **Сортировка:** проекты — по приоритету (самый высокий у незавершённых эпиков),
  затем по названию; эпики — по приоритету, статусу, ключу; истории — по приоритету и
  ключу. Приоритеты — пиктограммами Jira; если они не грузятся — цветной кружок (от
  красного к серому) с названием в подсказке.
- **Подсчёты.** Задачи истории — связанные с ней любой из связей настройки «Связи
  задачи с историей» (список через запятую; по умолчанию `Relates, is subtask of`, в
  любую сторону). Связь узнаётся по названию типа в Jira или по подписи, которую Jira
  показывает на странице задачи («relates to», «is subtask of»). Эпики и другие истории
  на том конце не в счёт. Итог эпика — по его задачам (Epic Link), каждая один раз, без
  историй: он совпадает с «Сохранёнными эпиками» и «По эпикам». Задача, связанная с
  двумя историями, видна в обеих. **Задачи истории из других эпиков** (или без эпика)
  видны в истории с пометкой «из эпика …» и входят в её итог, но не в итоги эпика и
  проекта — поэтому сумма по историям может быть больше итога эпика. Задачи, которые
  не удалось загрузить (нет прав, удалены), — в подсказке истории «не загружены». «Без
  истории» — задачи эпика, у которых нет истории в этом эпике.
- **Вехи:** у эпика — срок исполнения, а без него плановое завершение (◇); у проекта —
  ближайшая из вех незавершённых эпиков (все готовы — самая поздняя).
- История без задач, но со своим спринтом — штрихованный отрезок по этому спринту,
  без оценки.
- «Готово» у истории считается по всем её задачам, включая закрытые в
  прошлых спринтах: на шкале их нет (она начинается с текущего спринта), и без
  счётчика история с выполненной работой выглядела бы пустой. По щелчку — список
  задач.
- **Заметки** к эпику и истории — комментарии Jira `(omg comment) текст` в той же
  задаче; действует последняя, прежние — история. Строка заметки под строкой эпика и
  истории: первые две строки текста, автор и дата, полный текст при наведении; ✎ —
  правка, «История (N)» — прежние заметки. Строка есть только у задач с заметкой;
  добавить заметку — ✎ в действиях строки.
  Заметка старше порога («Настройки» → «Заметка устарела через, дней», по умолчанию
  14) помечена «заметке N дн.». Правка публикует новый комментарий в ту же задачу
  (Jira разошлёт письмо наблюдателям — форма предупреждает); старая заметка остаётся
  в истории. Заметки эпика в проект не поднимаются, у проекта заметок нет. Галочка
  «Заметки» на панели ракурса скрывает строки заметок.

## Сводка

Вкладка **«Сводка»** отвечает на четыре вопроса после каждого обновления: что изменилось,
что близко к завершению, где опаздываем и что с ресурсами. Глазами на диаграмму смотреть
не нужно.

- **Опоздание считается только от срока исполнения** (Due date) — это обещание заказчику.
  Главная мера — **запас до срока**: срок исполнения минус прогноз 85%, в неделях; меньше
  нуля — опаздываем. Рядом — **шанс успеть**: доля прогонов Монте-Карло, закончившихся не
  позже срока. Цвет эпика: зелёный — шанс от 85%, жёлтый — от 50%, красный — ниже или срок
  уже прошёл; отдельно — без срока, без прогноза и готовые.
- **Прогноз детерминирован**: зерно генератора — ключ эпика, отсчёт — понедельник текущей
  недели. На одинаковых данных в пределах недели даты одинаковы, поэтому сдвиг прогноза в
  сводке — настоящий, а не шум случайных прогонов. Шанс и запас показаны и в карточке эпика.
- **История.** После каждой синхронизации состояние каждого эпика (счётчики, прогноз, шанс,
  запас, команды) пишется в журнал (30 дней) и в недельную запись (104 недели) — в той же
  транзакции, что и данные. Удаление эпика из выбора историю не стирает.
- **История задним числом.** После «Скачать заново» и при первой синхронизации новой версии
  прошлые недели восстанавливаются: объём — по датам создания задач, остаток — по датам
  закрытия, поток команд — только до той недели. Поэтому тренды видны сразу. Ограничения:
  срок исполнения и состав команд берутся текущие; задачи, перенесённые между эпиками,
  учитываются по текущему эпику; недели с историей потока короче 12 недель считаются
  ориентировочными. Настоящие записи восстановлением не перезаписываются.
- **С чем сравниваем.** По умолчанию — с последним просмотром сводки: при открытии вкладки
  база фиксируется, а отметка просмотра сдвигается на последнюю синхронизацию. Ушли и
  вернулись без обновления — блок «Что изменилось» пуст. Переключатель «За 7 дней» сравнивает
  с последней синхронизацией не позже недели назад (в первые дни — с восстановленной
  недельной записью, с пометкой).
- **Что на вкладке:** итог по цветам; **«Требует внимания»** — до 7 самых важных сигналов
  (критичные, затем «внимание», по величине); свёрнутые блоки по группам; **таблица
  портфеля** — от худшего запаса, с мини-графиком запаса за 12 недель, шансом, прогнозом
  85%, сроком и готовностью. Клик по сигналу или строке открывает карточку эпика.
- **Сигналы:**
  - *что изменилось* — статус, эпик добавлен или завершён, рост и сокращение объёма, сдвиг
    прогноза 85% на неделю и больше, изменён срок исполнения, новые повторные переносы,
    закрытые задачи;
  - *близко к завершению* — прогноз 85% в пределах 2 недель или готово от 90%; «застрял на
    финише», если при этом 3 недели ничего не закрыто;
  - *где опаздываем* — срок прошёл, шанс ниже 50% (критично) или ниже 85%, запас тает
    3 недели подряд, застой (3 недели без закрытий), хронические переносы (задачи в 3+
    спринтах);
  - *ресурсы* — перегруз человека (единственный сигнал с именем), простой команды рядом с
    опаздывающим эпиком, распыление потока команды по эпикам, команда-узкое место (чаще
    всех замыкает прогноз в нескольких эпиках), задачи у уволенных, задачи текущего спринта
    без исполнителя;
  - *качество данных* — нет срока, много задач без оценки, мало истории потока, люди без
    команды, давно не обновлялось, закрытые Agile или Tempo API. Блок есть всегда: молчание
    сводки должно значить «всё хорошо», а не «нет данных».
- **«Принято».** У каждого сигнала кнопка «Принято» (появляется при наведении): сигнал уходит
  из «Требует внимания», в блоке остаётся зачёркнутым. Он вернётся сам, если ухудшится сверх
  порога — шанс упадёт ещё на 10 пунктов, опоздание вырастет ещё на неделю, объём ещё на
  5 задач и т. п.; у сигналов без величины — если поменяются их параметры. Исчезнувший и
  вернувшийся сигнал — новый случай. «Вернуть» снимает отметку.
- **Счётчик на вкладке.** После «Обновить» на вкладке «Сводка» — число новых сигналов
  «критично» и «внимание», которые ещё не показывались и не приняты. Открыли сводку — счётчик
  обнулился.
- **«Скопировать отчётом»** — в шапке сводки, в Markdown или простым текстом: дата, с чем
  сравниваем, итог по цветам и «Требует внимания» со ссылками на эпики в Jira. Отчёт вставляется
  в мессенджер или письмо; сам плагин никуда ничего не отправляет.
- **Точность прогнозов** — свёрнутый раздел внизу «Сводки». Для каждого завершённого эпика
  прогнозы 85%, сделанные за 8, 4 и 2 недели до финиша (из недельной истории, в том числе
  восстановленной), сравниваются с фактической датой завершения: ✓ — уложились, ✗ — нет.
  Итог — доля попаданий, ожидаемо около 85%: заметно ниже (меньше 75%) — прогноз оптимистичен,
  заметно выше (больше 95%) — перестраховывается; меньше 5 сравнений — выводы делать рано.
  Дата финиша — дата завершения эпика в Jira, а если её нет — дата закрытия последней задачи.
  Проверка идёт по истории, поэтому эпик, убранный из выбора после завершения, в ней остаётся;
  убранный до завершения — нет: его финиша плагин не видел.
- **Автообновление** (по желанию, «Настройки» → «Автообновление»): один раз за рабочий день,
  как только Jira доступна. Jira открывается только через VPN, поэтому обновление не
  привязано к точному времени: каждые 15 минут в заданном окне (по умолчанию будни,
  9:00–18:00) фоновый скрипт лёгкой пробой `<Jira>/status` проверяет, отвечает ли Jira
  (любой ответ — доступна, ошибка сети или 5 секунд без ответа — нет). Без VPN — тихо ждёт.
  Когда Jira ответила, синхронизирует **страница плагина** (фоновый скрипт Chrome усыпляет):
  открытая — по сообщению, закрытая — в неактивной вкладке, которая закрывается сама, если
  вы её не открыли. После — уведомление с числом новых сигналов; «войдите в Jira» и прочие
  ошибки — не чаще раза в день; обрыв VPN посреди обновления — молча, база не меняется,
  повтор на следующей проверке. Ручное обновление в этот день тоже считается. Если за день
  Jira так и не ответила, «Сводка» пишет «Данные от …: Jira была недоступна — проверьте VPN».
  Нужны разрешения `alarms` и `notifications`.
- **Одна синхронизация на все вкладки.** Синхронизация идёт под общим замком
  (`navigator.locks`): если одна вкладка плагина уже обновляет данные, вторая не запускает
  параллельную выгрузку, а пишет «Идёт обновление в другой вкладке», ждёт и перечитывает
  данные. Остальные открытые вкладки узнают о завершённой синхронизации и перерисовываются.
- **Пороги** всех сигналов — в «Настройках», карточка «Сводка»; пустое поле — значение по
  умолчанию. Пороги и таймаут запросов переносятся экспортом и импортом конфигурации.
- **Графики тренда** (одна точка — одна неделя; восстановленная история бледнее,
  ориентировочные недели — пунктиром; на каждой точке подсказка с датой, значением и
  изменением с прошлой недели):
  - **Тренд запаса до срока** — под таблицей портфеля: одна линия на эпик, по умолчанию
    жёлтые и красные (не больше 8), ноль выделен — это обещание. Клик по названию в легенде
    включает и выключает линию. Значок ⇅ — неделя, когда перенесли срок исполнения: скачок
    запаса после неё — не улучшение.
  - **Как менялся прогноз** — по клику на строку портфеля: коридор между прогнозом 50% и 85%,
    линия 85%, срок исполнения ступенькой (перенос срока виден ступенькой); кружок — неделя,
    с которой прогноз позже срока.
  - **Сделано против объёма** — там же: всего задач и готово по неделям; видно, почему уезжает
    срок — растёт объём или падает поток.

## Как считается таймлайн

- Колонки — **временные секции** одинаковой длины, а не спринты. Шаг секции —
  **ритм спринтов**: самое частое число дней между началами соседних спринтов
  одной доски (обычно 14). Именно ритм, а не длительность: Jira обычно ставит
  конец спринта накануне следующего старта (05.11–18.11, затем 19.11–02.12), то
  есть длительность 13 при ритме 14, и шаг на день короче копил сдвиг — примерно
  каждые 13 колонок появлялась лишняя пустая секция. Если стартов слишком мало
  (одна доска с единственным спринтом), шаг считается по длительности, как
  раньше. Отсчёт идёт от начала самого раннего из спринтов, **идущих сегодня**
  (по дням, конец включительно) и имеющих типовую длину (допуск — день, потому
  что длительность бывает на день короче ритма) — так недельный спринт одной
  команды не сдвигает шкалу для остальных; если таких нет — от любого идущего
  сегодня, иначе от текущего спринта по общим правилам.
- Всё, что идёт сегодня, всегда в секции «текущий». Остальные незакрытые
  спринты попадают в ту секцию, куда приходится их середина. Спринт,
  закончившийся до сегодня, на график не попадает, даже если в Jira он ещё не
  закрыт.
  Так спринты **разных команд**, идущие в одно время, оказываются в одной
  колонке — в заголовке секции они перечислены с цветной меткой команды (дат в
  заголовке нет: расчётный период секции с реальными границами спринтов не
  совпадает; текущая секция помечена словом «текущий»), а в
  строке проекта показаны отдельными отрезками. Если у команды спринты короче
  шага, в секции будет несколько её отрезков подряд.
- Шкала строится по **всей выгрузке** (задачи целевых эпиков и задачи людей вне
  их), поэтому колонки одинаковы на «По эпикам» и «По людям» и не меняются от
  фильтров и снятых галочек.
- Хвост секций, где нет ни одной задачи, отбрасывается; пустые секции между
  занятыми остаются (шкала времени честная). Спринты без дат собираются в
  последнюю колонку «Без дат».

## Команды

Если доска недоступна пользователю или удалена в Jira, её имени в справочнике
нет. В этом случае имя выводится **из названий её спринтов**: берётся слово,
которое чаще всего встречается в них (числа, даты и слово «спринт»
отбрасываются), например «20.2026 WEB[08.10 - 21.10]» → **WEB**. Такое имя
подчёркнуто пунктиром, в подсказке — номер доски. Если вывести не удалось,
остаётся «#id».

**Источник команд — Tempo, если он установлен.** При синхронизации плагин
запрашивает `/rest/tempo-teams/2/team` и состав каждой команды
(`/rest/tempo-teams/2/team/{id}/member`), учитывая только действующие членства
по датам. Команда человека берётся из Tempo по ключу, логину или отображаемому
имени; если человек числится в нескольких командах, берётся самая
малочисленная — команда «по умолчанию» обычно самая большая. Выключается
галочкой «Брать команды из Tempo» в настройках; если Tempo нет или нет прав,
синхронизация не прерывается и работает запасной способ.

Запасной способ: команда — это **доска** (rapid board), на которой заведён спринт: у спринта в поле задачи
есть `rapidViewId`, у спринта с доски — `originBoardId`. Названия досок
подтягиваются при синхронизации (`/rest/agile/1.0/board`) и хранятся в
IndexedDB (`boards`); если Agile API недоступен, команда подпишется как `#id`.

- **Команда спринта** красит отрезки в строках проектов и метки в заголовках
  секций; легенда — над диаграммой. Цветов восемь, дальше идут по кругу.
- **Команда исполнителя** — доска, на которой лежит больше всего его задач
  (считаются и прошлые спринты). Кто ни разу не был в спринте — «Без команды», в
  конце списка.
- Задачи **без спринта** учитываются в итогах слева, а на диаграммах раскладываются так:
  - **в работе** (любой статус категории Jira «В работе»: «В работе», «Анализ», «Ревью»,
    «Тест» и т. п.) — в секцию **«текущий»**, отдельным серым отрезком в штриховку
    **«Вне спринта»**. Так работают канбан-команды, например аналитики: их задачи
    не привязаны к спринтам, но делаются сейчас. Во всплывающем списке у таких задач
    пиктограмма ⊘ с подсказкой. Они входят в загрузку человека в текущей секции
    (перегруз, окно «кто может подменить»), а в строку «Прочие» попадают и канбан-задачи
    из чужих эпиков;
  - остальные **невыполненные** — в отдельную колонку **«Бэклог»** справа от спринтов;
  - **готовые** — никуда: закрытая задача вне спринта никого не интересует. Статусы,
    которые плагин считает готовыми, хотя Jira относит их к «В работе» (On Prod), тоже
    считаются готовыми.

  Строка «задач без спринта» в подсказке считает только бэклог. Команду канбан-сотрудника
  по доске не определить — задайте её в Tempo или на вкладке «Команда».
- Заливка полосы слева — **доля готовых задач** в ячейке: зелёная часть — готово,
  остальное — жёлтое (у эпика) или голубое (у проекта / человека). Доля считается
  по оценке, а если оценок нет — по количеству задач; при наведении видно
  «Готово: N из M». Бэклог по определению без готовых, поэтому без заливки.
- **История потока** (шаг 1 прогноза сроков). При синхронизации выгружаются
  завершённые задачи людей за окно, заданное в настройках («Окно истории потока»,
  по умолчанию 52 недели): JQL `assignee in (…) AND resolutiondate >= -52w`.
  Люди берутся из команд Tempo, а если их нет — из исполнителей выгрузки.
  Хранится ключ задачи, дата завершения, исполнитель, эпик и проект — этого
  достаточно, чтобы посчитать недельный поток команды и долю потока на эпик.
  В настройках показана диагностика: сколько завершений выгружено, за сколько
  недель и по скольким людям, а также предупреждение, если у готовых задач
  целевых эпиков нет даты завершения (так ведут себя статусы вне категории
  «Готово», например «On Prod») — их поток не виден.
- **User Story не считаются задачами.** Истории — контейнеры для задач, которые
  и так посчитаны, поэтому задачи этого типа исключены из числа задач эпика в
  «Сохранённых эпиках» и в карточке по «+» (по проектам Jira, готовность,
  оценки, «задач со списаниями») и из прогноза сроков (недельный поток команд,
  доля эпика, гистограмма, остаток задач). Списанное на истории время остаётся в
  сумме «Списано» — это реально потраченные часы. Список типов — «Настройки» →
  «Типы задач, не учитываемые в подсчётах» (через запятую, без учёта регистра,
  по умолчанию `User Story`). Счётчики списка пересчитываются сразу после
  сохранения настроек; тип задачи хранится и в истории потока, поэтому для
  прогноза исключение действует после «Обновить». Диаграммы «По эпикам» и «По
  людям» по-прежнему показывают все задачи. На «По эпикам» задачи этих типов тоже
  не считаются: полосы, подсказки (их JQL-ссылки дополняются `issuetype not in (…)`,
  чтобы число совпадало с Jira), люди под эпиком (человек только с историями строкой
  не выводится), задачи вне спринта в работе и ⚡ критический путь. Так итог эпика
  одинаков в списке, карточке, «Сводке» и на диаграмме. Загрузка людей — окно ⇄,
  сигналы «перегруз» и «простой команды» в «Сводке» — тоже считается без них:
  оценка истории дублирует оценки её задач. «По людям» показывает все задачи
  человека, включая истории.
- **Поток команд и доля эпика** в карточке эпика (по «+»). Из истории завершений
  считается недельный поток каждой команды (медиана задач в неделю и пик) и доля
  этого потока, уходящая на эпик: завершённые задачи эпика к всем завершённым
  задачам команды. Считается в **задачах**, а не в часах — на той же оси,
  что и будущий прогноз сроков. Берутся только полные недели: текущая и первая
  неполная отбрасываются, недели с нулём остаются. Под таблицей — границы окна и
  число полных недель, с предупреждением, если их меньше двенадцати.
- **Доля считается за период активности эпика**, а не за всё окно истории: окно
  может быть годом, а эпик прожил в нём пару месяцев — деление на годовой поток
  команды занижает долю в разы. Период = от первой недели с завершениями эпика до
  последней (у незакрытого эпика — до конца окна: он ещё в работе); нули внутри
  периода остаются, паузы — часть темпа. В подсказке строки видны все три числа:
  за период активности, за последние 8 недель (текущий темп) и за всё окно
  истории. Прогноз берёт самую свежую доступную оценку: последние недели →
  период активности → всё окно.
- **Выбор команд** — чипы сразу под заголовком «Поток команд и доля эпика».
  Можно выбрать одну или несколько команд («Все команды» сбрасывает выбор). Выбор
  пересчитывает всё ниже: невыбранные строки таблицы приглушаются, гистограмма
  суммирует только выбранные команды, период активности и **прогноз срока**
  считаются заново. Остаток задач эпика в прогнозе делят только выбранные команды
  (пропорционально их вкладу в эпик), а недельный поток каждой берётся за текущий
  период их работы над эпиком — от самой ранней недели с их завершениями до конца
  окна, но не короче 12 недель. Под прогнозом написано, по каким командам и за
  какие недели он посчитан.
- **Готовые задачи по неделям** — гистограмма в карточке эпика под таблицей потока.
  Столбец = полная неделя окна, высота = завершённые задачи выбранных команд,
  жёлтая нижняя часть = задачи этого эпика. Подсказка на столбце показывает
  границы недели и оба числа. Недели вне периода активности эпика приглушены — видно, по какому
  отрезку посчитана доля.
- **Прогноз срока** в карточке эпика. Остаток незавершённых задач распределяется
  между командами пропорционально их вкладу в эпик; каждая команда симулируется
  по своей истории: в каждом из 10 000 прогонов недели тянутся с возвратом, и
  неделя даёт «поток × доля потока» задач эпика. Срок прогона — **максимум** по
  командам: эпик готов, когда закончит последняя. Показываются перцентили 50, 85
  и 95 в неделях и датах, строка «чаще всех замыкает» (узкое место) и
  оговорка про зависимости. Меньше 5 полных недель истории — прогноз не строится,
  меньше 12 — предупреждение.
- **Списания по командам (часы)** в карточке эпика (по «+»): для каждой команды Tempo —
  сколько её участники списали на этот эпик и какую часть ёмкости это составило.
  Списания берутся из ворклогов самого эпика и всех его задач начиная с даты
  создания эпика; автор ворклога сопоставляется с командой по ключу, логину или
  имени. Ёмкость = участники команды × длительность спринта (рабочих дней) ×
  часов в дне × число спринтов, прошедших с создания эпика (длина спринта в
  календарных днях берётся из самих спринтов). Списания людей вне команд Tempo
  показываются отдельной строкой без процента. Считается по запросу при открытии
  карточки и кэшируется до следующего «Обновить».
- **Комментарии эпика** — пиктограмма 💬 рядом с названием эпика на вкладках
  «По эпикам». Окно с полем ввода и кнопкой «Сохранить»
  (комментарий уходит в Jira через `POST /rest/api/2/issue/{key}/comment`) и
  последними пятью комментариями из Jira в прокручиваемой зоне. В поле работает
  **упоминание через @**: после `@` открывается список пользователей Jira
  (`/rest/api/2/user/picker`), выбор стрелками и Enter/Tab или мышью вставляет
  разметку `[~логин]`, по которой Jira уведомляет человека; в списке
  комментариев она показывается как `@логин`. Это единственное место, где
  расширение **пишет** в Jira.
- **Оценка на вкладке «По людям» — это остаток работы**, а не план: в суммах по
  секциям, в итогах человека и его эпиков берётся **Remaining estimate**, если
  поле заполнено, и **Original estimate**, если оно пустое. Нулевой остаток —
  заполненное значение: у доделанной задачи работы действительно не осталось, и
  в загрузку она не добавляется. Для оценки в story points остатка в Jira нет —
  работает обычная настройка. Остальные вкладки («По эпикам», «Поиск») считают
  по выбранному в настройках полю. Пояснение выведено над диаграммой.
- **Синхронизация не портит данные при обрыве.** «Обновить» и «Скачать заново» сначала
  собирают всё в памяти и только потом записывают все хранилища одной транзакцией
  IndexedDB. Если посреди выгрузки отвалился VPN или сеть, синхронизация прерывается
  с сообщением «Jira недоступна — проверьте VPN и сеть», а база остаётся такой, какой
  была. Необязательные источники (Tempo, доски, история потока, задачи в чужих
  эпиках) при ошибке ответа Jira по-прежнему пропускаются, но недоступность Jira
  прерывает всё — иначе записались бы неполные данные. У каждого запроса таймаут
  30 секунд: без VPN запрос иначе висел бы больше минуты.
- **Две вкладки плагина не затирают настройки друг друга:** изменения настроек в одной
  вкладке сразу видны в другой.
- **Проверка доступности API** перед каждой выгрузкой («Обновить» и «Скачать заново»).
  Лёгкие пробы, которые ничего не качают: `/rest/api/2/myself` и
  `/rest/api/2/search` — без них выгрузка невозможна, синхронизация останавливается
  с понятной ошибкой; `/rest/agile/1.0/board` и `/rest/tempo-teams/2/team` —
  необязательные источники: выгрузка идёт дальше, но в строке итогов (красной)
  прямо сказано, что именно закрыто и чем это грозит: без Agile API не подтянутся
  доски и даты будущих спринтов, без Tempo API команды берутся из вкладки
  «Команда». Выключенный флажок «Брать команды из Tempo» ошибкой не считается.
- **Команды вручную.** Справочник команд задаётся в «Настройках» → «Поля» →
  **Команды** (по одной в строке или через запятую). На вкладке «Команда» у
  каждого сотрудника появляется колонка **Команда** — выпадающий список из этого
  справочника; выбор сохраняется в профиле. На вкладке «По людям» команда
  человека берётся в порядке: **ручная команда → Tempo → доска**, где больше его
  задач. Так вкладка остаётся разбитой по командам даже там, где Tempo API закрыт,
  а ручной выбор всегда сильнее автоматического — если Tempo записал человека не
  туда, исправление на вкладке «Команда» сразу видно на диаграмме.
- **Перегрузка спринта** на вкладке «По людям»: если суммарные оценки человека в
  секции (целевые эпики плюс прочие) больше ёмкости спринта — **длительность
  спринта в рабочих днях × часов в дне** из настроек, — секция обводится жирным
  красным, в подсказке видны нагрузка и ёмкость. Для оценки в story points
  подсветка выключена.
- **Веха завершения** эпика на вкладках, где строки — эпики: срок исполнения
  (Due date), а если его нет — плановое завершение (Planned End). Веха по
  плановому завершению — с флажком «◇» вместо «◆», точечной линией и подсказкой
  «Плановое завершение …»; если заполнены обе даты и они различаются, в подсказке
  вехи — обе. ⚡ «не укладывается в срок» считает ёмкость до той же даты. «Сводка»,
  шанс успеть и запас по-прежнему считаются только от срока исполнения: эпик с
  одним плановым завершением там «без срока». Пунктирная
  вертикальная линия через строку эпика и его вложенные строки, на строке эпика
  — флажок с датой. Положение — пропорционально внутри секции (у секции есть
  календарные границы). Цвет: красный — срок прошёл или ближе 14 дней, серый —
  дальше, зелёный — эпик уже готов. Срок раньше текущего спринта — флажок «◀» у
  левого края первой секции, позже последней — «▶» у правого края последней
  датированной секции; в «Без дат» и «Бэклоге» вехи нет. Подсказка — точная
  дата и «через N дн.» / «просрочен на N дн.».
- Клик по любой полосе на вкладке по эпикам (жёлтой у эпика, голубой у проекта,
  в бэклоге) открывает список задач этой ячейки: ключ и название со ссылками в
  Jira (новая вкладка), статус, исполнитель, оценка; готовые задачи зачёркнуты.
- Задачи из уже закрытых спринтов в полосы не попадают, но входят в общие
  суммы эпика/исполнителя.
- **Отменённые** задачи (Cancel / Cancelled / Отменена) в количестве задач
  учитываются, а в суммах дней — нет: работа по ним не делалась. Для счётчиков
  «Готово» они считаются готовыми.
- «Готово» в счётчиках задач определяется **по названию статуса**, а категория
  Jira — лишь запасной признак. Так «On Prod» попадает в готовые, даже если в
  Jira этот статус остался жёлтым (`indeterminate`).

## Статусы эпиков

Jira Server через REST отдаёт только цвет **категории** статуса (`new`,
`indeterminate`, `done`) — индивидуальных цветов у статусов там нет. Поэтому
цвет лейбла и порядок сортировки заданы таблицей в
[`src/js/status.js`](src/js/status.js):

| Статус | Цвет лейбла | Место в списке |
|---|---|---|
| В работе, In Progress, Разработка | синий | 1 |
| Бизнес тест, Тестирование, QA, Review | жёлтый | 2 |
| незнакомый статус в работе | серый | 3 |
| Сделать, To Do, К выполнению, Open | серый | 4 |
| New, Новый, Backlog | фиолетовый | 5 |
| Готово, Закрыто, Выполнено, Done, **On Prod**, На проде, Deployed, Production, **Cancel**, Cancelled, Отменена | зелёный | 6 |

Названия сверяются без учёта регистра, дефисов и «ё»: сначала точным
совпадением, затем вхождением с начала слова — поэтому «На тестировании»
попадает в «тестирование», а «Preprod testing» **не** попадает в «prod».
Статус, которого нет в таблице, получает место и цвет по категории из Jira.
На вкладке «По людям» сортировка прежняя — по суммарной оценке.

Эта же таблица решает, попадает ли задача в счётчик «Готово» в подсказке:
**название статуса важнее категории**. В Jira завершающие статусы потока часто
остаются жёлтыми (`indeterminate`) — «On Prod» тому пример, — и по категории они
бы в готовые не попали.

Если в вашем потоке есть свои завершающие статусы, их не нужно править кодом:
впишите их через запятую в поле **«Статусы, означающие “Готово”»** на вкладке
«Настройки». Для остального (цвет и порядок незавершённых статусов) правьте
`names` нужного правила в `status.js`.

## Ограничения

- Задачей эпика считается задача с заполненным **Epic Link**. Подзадачи,
  у которых Epic Link пуст, не скачиваются — иначе их оценки удваивали бы
  оценку родителя.
- Спринтом задачи считается **последний** спринт в поле Sprint (соглашение
  Jira: текущий спринт задачи идёт в списке последним).
- Удалённые в Jira задачи из локальной базы не исчезают до «Скачать заново».
- Расширение читает Jira; пишет только комментарии и только по явному действию:
  окно 💬, «Проект…», «Переименовать…» и заметки на ракурсе «Эпик — история». Перенос задач
  и изменение оценок не предусмотрены.
